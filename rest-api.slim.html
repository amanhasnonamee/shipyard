01
Where REST Came From
TAG DEEP

Almost every REST "rule" people repeat is a consequence of a specific historical problem. Knowing the problems turns arbitrary conventions into reasoning you can apply to new cases.

The problem before REST

Through the 1980s and 90s, making one program call another over a network meant Remote Procedure Call (RPC) systems: Sun RPC, CORBA, DCOM, Java RMI, and later SOAP. The idea was appealing — make a network call look exactly like a local function call. The problems were structural:

  1. Tight coupling. Client and server shared a generated interface definition. Change the server's method signature and every client broke, so both had to be deployed in lockstep. On the public internet, where you don't control your clients, that's fatal.
  1. The abstraction lied. A local function call can't take 4 seconds, fail because a router died, or arrive twice. Hiding the network made developers write code that ignored latency, partial failure, and retries — the hardest realities of distributed systems.
  1. Enormous complexity. SOAP required WSDL contracts, XML envelopes, and a stack of WS-\* specifications. Simple things took a lot of ceremony and specialized tooling.
  1. Infrastructure couldn't help. Every call was a POST of an opaque XML body to a single endpoint. Caches, proxies, and load balancers could see nothing meaningful, so none of the web's existing infrastructure could optimize or route anything.

Meanwhile, the World Wide Web — a wildly larger, more heterogeneous, more long-lived distributed system — was working extraordinarily well. Someone asked why.

What REST actually is: six constraints [DEEP]

Fielding defined REST as constraints, each with a purpose. This is the part almost nobody learns, and it's the part that lets you make design decisions instead of copying conventions.

ConstraintWhat it requiresWhat it buys
Client–serverSeparate UI concerns from data storage concernsThey evolve and scale independently
StatelessnessEvery request carries everything needed to process it; the server keeps no client session state between requestsAny server can handle any request → horizontal scaling, easy failover, simpler recovery
CacheabilityResponses declare whether they're cacheableEliminates round trips entirely. The single biggest reason the web scales
Uniform interfaceThe same small set of operations for all resources, with self-descriptive messagesGeneric infrastructure (browsers, proxies, CDNs, caches) works with *any* API without custom knowledge
Layered systemClient can't tell whether it's talking to the origin serverYou can insert load balancers, gateways, caches, and CDNs transparently
Code-on-demand (optional)Server can ship executable code to clientsThis is literally JavaScript in web pages

The insight to carry: REST optimizes for evolvability and scale in a system where you don't control the clients and can't coordinate deployments. That's why it's verbose and chatty compared to RPC, and why it's the right trade for a public API and often the wrong trade for two microservices in the same cluster (Part 12).

The framing worth being able to say

*"REST isn't a protocol or a standard — it's the set of architectural constraints Roy Fielding identified as the reason the web scales, published in 2000. The two that do most of the work are statelessness, which lets any server answer any request, and the uniform interface, which lets generic infrastructure like caches and proxies understand traffic they know nothing about. And it's worth being honest that most APIs called REST aren't, strictly — they drop hypermedia and keep the resource model and HTTP semantics, which turned out to be the valuable part."*

02
The Core Mental Model
TAG DEEP★ INTERVIEW GOLD

Five ideas. This is the most important section in the document.

Idea 1: A resource is a *thing*, and what you receive is a *representation* of it

A resource is any concept worth naming: a book, a user, an order, a search result, today's weather. It is identified by a URL. Crucially, the resource is the abstract thing; what crosses the network is a representation of it — usually JSON, but potentially XML, CSV, HTML, or a PDF of the same underlying resource.

This is the entire meaning of the name: REpresentational State Transfer — you transfer representations of resource state.

Three consequences that shape all API design:

  • URLs name things, not actions. /books/42 is a thing. /getBook?id=42 is a function call wearing a URL costume — it's RPC, not REST. The verb belongs in the HTTP method, which already exists for exactly this purpose.
  • One resource can have many representations. The same /books/42 can return JSON to an app and CSV to a spreadsheet, selected by the Accept header (content negotiation, Part 5). The resource didn't change; the representation did.
  • The representation is not the database row. This is a subtle and important point: your API is a *contract*, deliberately decoupled from your storage. Exposing raw table rows means every schema change breaks clients — precisely the coupling REST exists to avoid.

Idea 2: The uniform interface — HTTP methods are the verbs, and their properties matter more than their names

REST deliberately uses a tiny, fixed set of operations for every resource. Which means the important thing to learn isn't the list of methods — it's the two *properties* that make them safe to use in an unreliable network.

MethodPurposeSafe?Idempotent?Has body?
GETRetrieve a representationYesYesNo
HEADLike GET, headers onlyYesYesNo
POSTCreate a subordinate resource; or any non-idempotent operationNoNoYes
PUTCreate or replace a resource at a known URLNoYesYes
PATCHPartially modify a resourceNoNot necessarilyYes
DELETERemove a resourceNoYesUsually no
OPTIONSAsk what's permitted (used by CORS preflight)YesYesNo

Safe means the request doesn't change server state — it's a read. This is why crawlers, browsers, and prefetchers will happily issue GET requests without asking, and why *a GET that deletes something is a genuine bug that will eventually be triggered by a link preview or a crawler.*

Idempotent means making the request N times has the same effect as making it once. This is the single most practically important concept in this table, because networks fail after the server acted but before the response arrived. The client cannot tell "it didn't happen" from "it happened but I didn't hear back." So:

  • PUT /books/42 with a full body: retrying is safe. Same final state.
  • DELETE /books/42: retrying is safe. Already gone is the desired state (return 404 or 204, either is defensible).
  • POST /books: retrying may create a second book. Not idempotent. Which is exactly why idempotency keys exist for payments and other critical creates (Part 11).

Understanding safety and idempotency is what lets you reason about retries, timeouts, and duplicate requests — the actual hard part of distributed systems, and the thing that separates people who *use* APIs from people who can *design* them.

PUT vs PATCH, since it's constantly confused: PUT means "here is the complete new state of this resource — replace it." Omit a field and you're saying it should be absent. PATCH means "here is a description of changes." Omit a field and you're saying "leave it alone."

Idea 3: Statelessness — the server remembers nothing between requests

Every request must carry everything needed to process it: identity, parameters, context. The server holds no per-client memory between requests.

terminal
Stateful (violates REST):                Stateless (REST):
  POST /login        → server stores      Every request carries a token:
       session in memory                    GET /orders
  GET /orders        → server looks up      Authorization: Bearer eyJ...
       "who is this connection?"
  ⚠ this client must now always
    reach the SAME server

What statelessness buys — and this is the reason it's non-negotiable at scale: any server can handle any request. So you can put ten identical servers behind a load balancer, kill one mid-traffic, deploy a new version gradually, and autoscale on demand. None of that works if request #2 depends on memory created by request #1 on a specific machine.

What it costs: every request re-sends authentication context, and the server may repeat work (like looking up the user) each time. That's the trade, and it's usually overwhelmingly worth it.

The common point of confusion worth being precise about: **"stateless" refers to *client session* state, not to data.** Of course your database has state. Storing sessions in a shared store (Redis, or a database) is also fine in practice — the constraint being honoured is that no individual *server* holds client state in its own memory.

Idea 4: Status codes are the response's type system

The status code tells the client what *kind* of thing happened, and the client should branch on the class before reading the body. Learn the five families first; the individual codes then mostly follow.

FamilyMeaningThe one thing to remember
1xxInformationalYou'll almost never see these
2xxSuccessIt worked
3xxRedirectionLook elsewhere
4xxClient error*You* sent something wrong — retrying identically won't help
5xxServer error*The server* failed — retrying may well work

That 4xx/5xx distinction is the load-bearing one: it tells a client whether to retry or to fix its request, and it tells you whether an alert should wake up an engineer. Returning 500 for a validation error trains clients to retry pointlessly and buries real outages in noise.

The codes worth knowing cold [DEEP]:

CodeNameUse when
200OKSuccessful GET, or PUT/PATCH returning the updated resource
201CreatedSuccessful creation — include a Location header pointing at the new resource
202AcceptedWork was queued, not completed (async jobs)
204No ContentSuccess with nothing to return — typically DELETE
301 / 308Moved PermanentlyThe resource has a new URL forever (308 preserves the method)
304Not ModifiedConditional GET: the client's cached copy is still valid (Part 11)
400Bad RequestMalformed syntax or unparseable body
401UnauthorizedNot authenticated — you didn't prove who you are (the name is a historical misnomer)
403ForbiddenAuthenticated but not permitted — we know who you are; you can't do this
404Not FoundNo such resource. Also used deliberately to hide existence from unauthorized users
405Method Not AllowedWrong verb for this URL — include an Allow header
409ConflictState conflict: duplicate unique field, concurrent edit, illegal state transition
410GoneIt existed and was deliberately removed
415Unsupported Media TypeYou sent a Content-Type the server can't accept
422Unprocessable ContentSyntax fine, but semantically invalid (failed business validation)
429Too Many RequestsRate limited — include Retry-After
500Internal Server ErrorAn unhandled failure. Never leak a stack trace here
502 / 503 / 504Bad Gateway / Unavailable / Gateway TimeoutUpstream failed, overloaded, or too slow

401 vs 403 is asked in almost every API interview: 401 means "I don't know who you are," 403 means "I know exactly who you are, and no."

Idea 5: An API is a published contract, and its hardest problem is change

The moment someone else depends on your API, you have made a promise. Clients you don't control — mobile apps that users won't update, scripts, partner integrations — will keep calling the shape you shipped.

So the central discipline of API design is backward compatibility, and the useful mental sorting is:

Safe (additive)Breaking
Adding a new endpointRemoving or renaming an endpoint or field
Adding an optional request fieldAdding a required request field
Adding a field to a responseChanging a field's type or meaning
Adding a new optional query parameterChanging default behaviour or default sort order
Adding a new enum value the client can ignoreMaking validation stricter
Relaxing validationChanging a status code for an existing condition

Notice that several "harmless" changes are breaking. Tightening validation breaks clients that were sending sloppy-but-accepted data. Adding an enum value breaks clients that hard-coded a switch over all values — which is why clients should be written tolerantly (ignore unknown fields, handle unknown enum values gracefully). This mutual discipline — servers add rather than change, clients tolerate rather than assume — is what "evolvability" means in practice, and it's the constraint Part 6's versioning strategies exist to serve.

HTTP: The Substrate REST Is Built On

REST is a way of using HTTP well. So you cannot be good at REST without genuinely knowing HTTP. This part is the foundation everything else stands on.

3.1 The anatomy of a request and response [DEEP]

Every HTTP exchange is text (in HTTP/1.1 — later versions compress it, but the model is identical). A request:

http
POST /v1/books HTTP/1.1                    ← method, path, version (the "request line")
Host: api.example.com                      ← headers: metadata about the request
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json             ← what I'm SENDING
Accept: application/json                   ← what I want BACK
Content-Length: 47
Idempotency-Key: 7f3c9a12-...
                                           ← blank line separates headers from body
{"title": "Dune", "author_id": 42}         ← body

And a response:

http
HTTP/1.1 201 Created                       ← version, status code, reason phrase
Content-Type: application/json
Location: /v1/books/1001                   ← where the new resource lives
ETag: "a3f9c2"
Cache-Control: no-store

{"id": 1001, "title": "Dune", "author_id": 42, "created_at": "2026-08-11T09:12:00Z"}

Four parts on each side: start line, headers, blank line, body. That's the whole protocol shape. Run curl -v against any API and you will see exactly this. Doing that once, deliberately, is worth more than reading three tutorials.

3.2 The headers that actually matter [RECOGNIZE — but know what each is *for*]

Request headers:

HeaderPurpose
HostWhich site on this server (mandatory in HTTP/1.1; enables virtual hosting)
AuthorizationCredentials — Bearer <token>, Basic <base64>
Content-TypeThe format of the body you are sending
AcceptFormats you can receive — the basis of content negotiation
Accept-EncodingCompression you support (gzip, br)
User-AgentWho's calling — useful for debugging and analytics
If-None-Match / If-Modified-SinceConditional GET for caching (Part 11)
If-MatchConditional write for optimistic concurrency (Part 11)
Idempotency-KeyClient-generated key so retried creates don't duplicate (Part 11)

Response headers:

HeaderPurpose
Content-TypeFormat of the body being returned
LocationWhere a newly created resource lives (with 201), or where to go (with 3xx)
Cache-ControlCaching rules — max-age, no-store, private, public
ETagAn opaque version identifier for this representation
Retry-AfterHow long to wait (with 429 or 503)
WWW-AuthenticateHow to authenticate (with 401)
AllowPermitted methods (with 405)
Access-Control-Allow-*CORS permissions (Part 7)
X-Request-IdCorrelation ID for tracing a request across services (Part 11)

The point of the table isn't memorization — it's that HTTP already has a well-designed mechanism for most cross-cutting concerns. People routinely reinvent caching, versioning, content negotiation, and conditional updates inside JSON bodies because they didn't know the protocol already solved it. Reaching for the existing mechanism is what "using HTTP well" means, and it's the difference between an HTTP API and an API that merely travels over HTTP.

3.3 Content negotiation [DEEP concept, RECOGNIZE syntax]

The client says what it wants; the server picks the best available representation:

http
Accept: application/json                    → JSON
Accept: text/csv                            → CSV export of the same resource
Accept: application/json; version=2         → one legitimate versioning approach (Part 6)

If the server can't satisfy it: 406 Not Acceptable. If the client *sends* a body in a format the server doesn't support: 415 Unsupported Media Type. Those two are easy to mix up — one is about the response, the other about the request.

3.4 Query parameters vs path segments vs headers vs body [DEEP]

Where does a piece of information belong? A rule that resolves nearly every case:

LocationForExample
PathIdentifying *which resource*/books/42/reviews
Query stringModifying *how* a collection is returned — filter, sort, paginate, shape?status=active&sort=-created_at&page=2
HeadersMetadata about the request itself — auth, formats, caching, tracingAuthorization, Accept
BodyThe data being created or updatedThe JSON of a new book

Two hard rules that follow: never put secrets in the query string (URLs are logged by servers, proxies, browsers, and analytics — a token in a URL is a token in a dozen log files), and never use a request body on GET (it's not reliably supported by intermediaries, and many clients and caches ignore it).

3.5 Exercises

  1. curl -v a public API (GitHub's is ideal: curl -v https://api.github.com/repos/torvalds/linux). Identify every part of the request and response by name.
  1. Deliberately trigger five different status codes against a real API: 200, 401, 404, 405, and 422 or 400. Record what each response body looked like.
  1. Send the same request with Accept: application/json and then Accept: application/xml to an API that supports both, and observe negotiation. Then send a nonsense Accept and get a 406.

04
Resources and URL Design

URL design is where most APIs reveal whether their author understood REST. It's also cheap to get right and expensive to change later, since URLs are the part clients hard-code.

4.1 The core rules [DEEP]

1. URLs identify nouns; HTTP methods provide the verbs.

terminal
✗ POST /createBook          ✓ POST   /books
✗ GET  /getBook?id=42       ✓ GET    /books/42
✗ POST /updateBook          ✓ PATCH  /books/42
✗ GET  /deleteBook?id=42    ✓ DELETE /books/42

The left column isn't merely unfashionable — it's actively worse, because it discards everything HTTP gives you for free: caches can't tell reads from writes, infrastructure can't retry safely, and a crawler following links can destroy data.

2. Use plural collection names consistently. /books is the collection; /books/42 is a member. Pick plural and never mix (/book/42 alongside /books is the kind of inconsistency that costs every client developer an hour).

3. Nest to express containment, but stop at two levels.

terminal
✓ /authors/7/books           the books belonging to author 7
✗ /authors/7/books/42/reviews/9/comments/3     unreadable, brittle, and unnecessary

Once a resource has its own identity, give it a top-level URL: /reviews/9/comments or /comments?review_id=9. Deep nesting encodes your data model into every client's code, which is exactly the coupling you're trying to avoid.

4. Prefer flat filtering to nesting for optional relationships. /books?author_id=7 and /authors/7/books can coexist; the query version is more flexible because it composes with other filters.

5. Conventions that reduce friction [RECOGNIZE]: lowercase paths, hyphens rather than underscores in path segments (/order-items), no file extensions (use Accept), no trailing slashes (pick one and redirect the other), and no verbs anywhere in a path.

4.2 Actions that aren't CRUD [DEEP — the honest hard case]

Real systems have operations that don't map cleanly onto create/read/update/delete: publish an article, cancel an order, send a password reset, retry a job, transfer money. This is where dogmatic REST advice becomes unhelpful, so here are the three legitimate approaches:

Option A — model the state change as a field update (most RESTful):

http
PATCH /orders/42
{"status": "cancelled"}

Good when the concept genuinely is a state field and any transition is permitted.

Option B — model the action as a sub-resource (usually best for real workflows):

http
POST /orders/42/cancellation
POST /articles/9/publication
POST /jobs/17/retries

This treats the *event* as a thing that can be created — which is honest, gives you somewhere to attach metadata (who cancelled, why, when), and stays idempotency-friendly.

Option C — an explicit action endpoint (pragmatic, widely used):

http
POST /orders/42/cancel
POST /payments/88/refund

Not strictly RESTful. Also what Stripe, GitHub, and most successful APIs do for genuine operations. It's clear, it's discoverable, and clarity beats purity.

The judgment to develop: use A when it's really a field, B when the action has its own data or history worth recording, and C when the operation is a genuine command and A/B would be contortions. Being able to defend the choice matters more than which one you pick — and "I chose C for clarity because the alternative was a fake resource nobody would understand" is a strong interview answer.

4.3 Common mistakes

  • Verbs in URLs (/api/getUsersList) — the single most common tell of an RPC-shaped API.
  • Inconsistent pluralization or casing across endpoints.
  • Exposing database internals: /tbl_users, or auto-incrementing IDs that let anyone enumerate every record (consider UUIDs or opaque IDs for anything sensitive).
  • Nesting five levels deep.
  • Returning different response shapes from the same endpoint depending on parameters — clients can't type that.
  • Using POST for everything, which throws away safety, idempotency, and caching in one move.

4.4 Exercise

Design the complete URL surface for a library system: books, authors, members, loans, reservations, and fines. Include: how to list a member's active loans, how to return a book, how to search books by title and availability, and how to pay a fine. For every action that isn't plain CRUD, write one sentence justifying which of options A/B/C you chose and why.

05
Representations, Errors, and Validation

5.1 Designing response bodies [DEEP]

Decisions to make once and apply everywhere — inconsistency here is what makes an API exhausting to consume:

json
{
  "id": "bk_1001",
  "title": "Dune",
  "published_year": 1965,
  "author": { "id": "au_42", "name": "Frank Herbert" },
  "tags": ["sci-fi", "classic"],
  "price": "12.99",
  "created_at": "2026-08-11T09:12:00Z",
  "updated_at": "2026-08-11T09:12:00Z"
}

The conventions embedded above, and why:

  • One naming style everywhere. snake_case or camelCase — pick one. (JSON leans camelCase; many backends emit snake_case. Either is fine; mixing is not.)
  • Timestamps in ISO 8601, UTC, with an explicit offset. "2026-08-11T09:12:00Z". Never a bare "11/08/2026" — ambiguous by locale — and never a naive local time.
  • Money as a string, or as an integer of minor units. JSON numbers are IEEE-754 doubles in most parsers, so 12.99 can arrive as 12.989999999999998. Send "12.99" or 1299 with the currency stated. This is a real bug that has cost real money.
  • Large integers as strings. JavaScript loses precision above 2^53, so 64-bit IDs must be strings if any client is JS — which, for a public API, they will be.
  • Prefixed or opaque IDs (bk_1001) are self-documenting in logs and prevent clients from doing arithmetic on your IDs.
  • Embed vs reference: embedding the author saves a round trip; referencing ("author_id": "au_42") keeps responses small. A common compromise is a small embedded summary plus an ?expand=author parameter for the full object.
  • Return the created/updated resource from POST/PUT/PATCH. It saves the client a follow-up GET and lets it see server-computed fields.
  • Avoid nulls-as-meaning. Distinguish "unknown," "not applicable," and "empty" deliberately, and document it.

Whether to wrap responses in an envelope ({"data": {...}}) is a genuine judgment call: an envelope gives you a stable place for metadata and makes collection responses uniform; skipping it is cleaner and lets HTTP carry the metadata it already has headers for. Choose one and apply it universally — a mixed API is the worst outcome.

5.2 Error responses [DEEP — the most neglected part of most APIs]

Errors are part of your contract, and consuming an API with bad errors is miserable. A good error tells the client three things: what kind of failure, whether retrying helps, and what to fix.

A solid shape (aligned with RFC 9457 *Problem Details for HTTP APIs*, worth adopting since it's a real standard):

json
{
  "type": "https://api.example.com/errors/validation-failed",
  "title": "Validation failed",
  "status": 422,
  "detail": "The request contained 2 invalid fields.",
  "instance": "/v1/books",
  "request_id": "req_8f2a1c",
  "errors": [
    { "field": "title",     "code": "required",  "message": "Title is required." },
    { "field": "published_year", "code": "range", "message": "Must be between 1450 and 2026." }
  ]
}

Rules that matter:

  1. Use the right status code. The body is for humans and debugging; the status code is for machines. A 200 response containing {"error": "not found"} is a broken API — every client, cache, and monitoring system will treat it as success. This is one of the most common serious API design errors.
  1. Machine-readable error codes ("required", "insufficient_funds") in addition to human messages. Clients must never parse your prose, because prose gets reworded.
  1. Report all validation failures at once, not the first one. Otherwise a form submission takes five round trips.
  1. Include a request/correlation ID so a user can report an error and you can find it in your logs instantly.
  1. Never leak internals — no stack traces, SQL, file paths, or library versions. That's both a security issue and a support burden.
  1. Be consistent. The same error shape from every endpoint, including from your gateway and framework defaults (which is easy to forget — test what a 404 on an unknown path returns, and what a malformed JSON body returns).

5.3 Validation [DEEP]

Validate at the boundary and reject early. Three layers, all necessary:

LayerChecksOn failure
SyntacticIs it parseable JSON? Right Content-Type?400, or 415
StructuralRequired fields present, correct types, within ranges, valid enums422 (or 400 — both defensible; be consistent)
Semantic / businessDoes the referenced author exist? Is this state transition legal? Does the user have enough balance?422, 409, or 403 depending on the reason

Two non-negotiable rules: never trust the client — every rule enforced in a UI must be re-enforced on the server, because anyone can call your API directly with curl. And validate with a schema, not hand-written if statements (pydantic, zod, JSON Schema) — hand-rolled validation drifts out of sync with your documentation immediately.

A note on the useful boundary: reject unknown fields or ignore them? Ignoring is more forgiving and better for evolvability; rejecting catches client typos early. Rejecting on write endpoints and ignoring elsewhere is a reasonable middle path — document whichever you choose.

Collections, Evolution, and Versioning

6.1 Pagination [DEEP — including why the obvious way is wrong]

Never return an unbounded collection. It will be small in development and catastrophic in production.

Offset pagination — the intuitive approach:

http
GET /books?limit=20&offset=40

Simple, allows jumping to page N, and has two real problems: it gets progressively slower as the offset grows (the database must generate and discard every skipped row — the same issue covered in the SQL curriculum), and it skips or duplicates items when the underlying data changes between requests, because "row 41" isn't stable.

Cursor (keyset) pagination — the correct default for large or changing data:

http
GET /books?limit=20&cursor=eyJpZCI6MTAwMSwiY3JlYXRlZCI6...

{
  "data": [ ... ],
  "next_cursor": "eyJpZCI6MTAyMSwi...",
  "has_more": true
}

The cursor is an opaque encoding of "where I left off" (typically the last item's sort key plus its ID as a tiebreaker). It stays fast at any depth and is stable under inserts. The trade-off: no jumping to an arbitrary page, which is usually fine for APIs (and is what every large API — Stripe, GitHub, Twitter — uses).

Whichever you choose: always include a default limit and a maximum limit, and return enough metadata for the client to continue.

6.2 Filtering, sorting, and shaping [RECOGNIZE]

http
GET /books?status=available&author_id=42&published_year__gte=1960
         &sort=-published_year,title
         &fields=id,title,author
         &expand=author
         &q=dune

Conventions worth adopting: a - prefix for descending sort; comma-separated multi-sort; fields for sparse fieldsets (saves bandwidth for mobile clients); expand for embedding related resources on demand; and q for free-text search. Keep the operator syntax for ranges simple and documented — this is an area REST left open, so the only wrong answer is being inconsistent.

Be aware that unbounded filtering and sorting is an availability risk: every filterable field should be indexed, or a client can trivially issue a query that scans your whole table.

6.3 Versioning [DEEP — a real trade-off with no consensus answer]

Because breaking changes eventually become necessary (Idea 5), you need a strategy.

ApproachExampleProsCons
URL path/v1/booksObvious, easy to route, trivially testable in a browser, cacheableArguably un-RESTful (the resource didn't change, so its identifier shouldn't); can lead to whole-API duplication
Custom headerX-API-Version: 2URLs stay stableInvisible in browsers and logs; easy to forget; harder to test by hand
Accept headerAccept: application/vnd.example.v2+jsonPurist-correct content negotiationVerbose, poorly understood, awkward tooling
Date-basedStripe-Version: 2026-08-11Fine-grained; clients pin a date and are upgraded deliberatelySignificant server-side complexity maintaining transformations
No versioningAdditive changes only, foreverSimplest for clientsRequires real discipline and a way to eventually retire things

Practical recommendation: /v1/ in the path for a public API, combined with a strong bias toward *never* needing `/v2/*. Version numbers are for genuine breaking redesigns, not for routine additions. Most successful APIs have one or two major versions across a decade, because they treated additive evolution as the default.

Whatever you choose, the operational discipline matters more than the mechanism: publish a deprecation policy (the Deprecation and Sunset headers exist for this), give long notice with real dates, monitor which clients still use the old version, and communicate directly with them. An API version you can't retire is a maintenance cost forever.

6.4 Documentation and contracts [DEEP]

An undocumented API doesn't functionally exist. The industry standard is OpenAPI — a machine-readable description of every endpoint, parameter, schema, and response:

yaml
paths:
  /books/{id}:
    get:
      summary: Retrieve a book
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: string }
      responses:
        '200':
          description: The book
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Book' }
        '404': { $ref: '#/components/responses/NotFound' }

Why it's worth the effort: from one document you get interactive documentation, generated client libraries in many languages, request validation, mock servers for frontend development before the backend exists, and automated contract tests. Frameworks like FastAPI generate it from your code and type annotations automatically, which removes the main excuse for not having it.

The rule that keeps documentation honest: generate documentation from the code or validate the code against the documentation. Hand-maintained docs in a separate wiki are wrong within weeks, and wrong documentation is worse than none because it's trusted.

Two different questions, constantly conflated: authentication is *who are you*; authorization is *what may you do*. 401 answers the first, 403 the second (Idea 4).

7.2 JWTs, honestly [DEEP — widely used, widely misunderstood]

A JWT is three base64url segments separated by dots: header.payload.signature.

terminal
eyJhbGciOiJIUzI1NiJ9  .  eyJzdWIiOiJ1c2VyXzQyIiwiZXhwIjoxNzY...  .  4f2Xk9...
   algorithm              claims: subject, expiry, scopes           signature

The critical facts, in order of how often they're gotten wrong:

  1. A JWT is signed, not encrypted. Anyone holding it can read the payload — paste one into any decoder. Never put secrets or sensitive personal data in a JWT.
  1. The signature proves it wasn't tampered with, which is the actual value: the server can verify it with a key instead of a database lookup.
  1. That statelessness is the whole point and also the whole problem: you cannot easily revoke a JWT. It's valid until it expires. If a token is stolen or a user is banned, they retain access until expiry. The standard mitigation is short-lived access tokens (5–15 minutes) plus a long-lived, *revocable*, database-backed refresh token — and if you find yourself maintaining a token denylist, you've reintroduced the database lookup you were avoiding, which is a legitimate signal that plain sessions might have been the better choice.
  1. Always validate: signature, exp (expiry), iss (issuer), and aud (audience). And pin the expected algorithm — historically, libraries that trusted the token's own alg header allowed attackers to set alg: none or downgrade RS256 to HS256 and forge tokens. Trust your configuration, never the token's claim about itself.
  1. Where you store it in a browser is a real trade-off, not a solved problem. localStorage is readable by any XSS on your page. An HttpOnly cookie is not readable by JavaScript but is sent automatically, so it needs CSRF protection (SameSite=Lax or Strict, plus a token for state-changing requests). The common professional choice is HttpOnly; Secure; SameSite cookies plus CSRF defence, because XSS is more common than CSRF and cookies at least remove the token-theft path.

7.3 Authorization models [RECOGNIZE]

  • RBAC (role-based): users have roles; roles have permissions. Simple, coarse, sufficient for most applications.
  • ABAC / policy-based: decisions from attributes (owner, department, resource state, time). Flexible, more complex.
  • Scopes: what a *token* is permitted to do (books:read, books:write) — this is OAuth's model and is orthogonal to what the *user* is permitted to do. Both checks are needed.
  • Ownership checks: the one people forget. "Is this user allowed to read *this specific* order?" Missing per-object checks is Broken Object Level Authorization — consistently the number one API vulnerability in the OWASP API Security Top 10, and the reason /orders/1002 must not return someone else's order just because you're logged in. Test this explicitly for every endpoint that takes an ID.

7.4 CORS — the thing that will confuse you at least once [DEEP]

CORS confuses everyone because it protects something other than what people assume.

The browser's same-origin policy blocks JavaScript on https://myapp.com from reading responses from https://api.other.com. This exists so that a malicious page can't use *your* logged-in browser to read your bank's API. CORS is the mechanism by which a server opts in to being read by a specific other origin.

Facts that resolve most confusion:

  • CORS is enforced by browsers only. curl, Postman, mobile apps, and your server ignore it entirely. "It works in Postman but not in my app" is the signature CORS symptom.
  • CORS is not a server-side security feature. It does not protect your API — attackers don't use browsers. It protects *users* from cross-origin reads. Your API still needs authentication and authorization.
  • The server grants permission with response headers, not the client:
http
Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 600
  • Preflight: for anything other than a "simple" request (custom headers, PUT/PATCH/DELETE, JSON content type), the browser first sends an OPTIONS request asking permission. Your API must handle OPTIONS and return the headers, or every non-trivial call fails before it's even sent. Seeing an unexplained OPTIONS in your logs is not an attack; it's this.
  • Access-Control-Allow-Origin: * cannot be combined with credentials. With Allow-Credentials: true you must echo a specific origin — and you must validate it against an allowlist, not reflect whatever the client sent, which would defeat the entire mechanism.

8.2 Project B — consume a real third-party API robustly

Pick a public API with authentication and rate limits (GitHub, Stripe test mode, TMDB, OpenWeather). Write a client that does all of the following, because this is what production API consumption actually requires:

  1. Reads credentials from environment variables, never hard-coded.
  1. Sets an explicit timeout on every request. (A missing timeout is the single most common production hang: a request with no timeout can wait forever.)
  1. Retries with exponential backoff and jitter — but only on 5xx, 429, and network errors. Never on 4xx, because a bad request will still be bad on the fourth attempt.
  1. Honours Retry-After when present.
  1. Paginates through a large collection using the API's own scheme, handling the last page correctly.
  1. Distinguishes and handles: network failure, timeout, 401 (bad credentials — stop and report), 403 (permission — stop), 404 (missing — may be fine), 429 (back off), and 5xx (retry).
  1. Caches responses where the API's Cache-Control/ETag headers permit it, using conditional requests to avoid re-downloading unchanged data.
  1. Logs each request's method, URL, status, and duration — without logging the token.

Definition of done: unplug your network mid-run and the client fails with a clear message rather than a stack trace; deliberately use a bad token and get a comprehensible error; and run it against a large collection to confirm pagination terminates.

9.1 The debugging decision tree

Always establish where the failure is before guessing why. Work outward from the simplest thing that could be true.

The request never gets a response (hangs or connection error).

  1. Is the server running and listening on the port you think? (curl localhost:8000/health)
  1. DNS resolving? (nslookup/dig) Right host, right port, right scheme (http vs https)?
  1. Firewall, security group, or container port mapping blocking it?
  1. Is the server bound to 127.0.0.1 instead of 0.0.0.0? (Inside a container, localhost means the container — the same trap as in the Docker curriculum.)
  1. Did you set a timeout? If not, you're not hanging — you're waiting forever.

4xx you don't expect.

CodeCheck first
400Is the JSON actually valid? Print the exact bytes you're sending
401Is the header spelled Authorization: Bearer <token> with the space? Token expired? Correct environment (test vs live keys)?
403Authenticated but lacking permission or scope — or an ownership check failing
404Typo in the path, missing /v1, wrong ID, trailing slash mismatch, or the object belongs to someone else and is being hidden deliberately
405Right URL, wrong method. Check the Allow header in the response
415Missing or wrong Content-Type — the most common cause of a "my POST doesn't work" report
422Read the error body; it should tell you exactly which fields failed
429You're rate limited. Read Retry-After and back off

5xx from your own API. Read the server logs, not the response — the response is deliberately vague. Find the request by its correlation ID. Then ask: unhandled exception, a downstream dependency failing, a timeout, or resource exhaustion (connection pool, memory, file handles)?

"It works in curl/Postman but not in my browser app." This is CORS in almost every case (Part 7.4). Check DevTools' console for the specific CORS message and whether an OPTIONS preflight failed. Second most likely: the browser is sending different headers, or cookies aren't being sent because of SameSite or a missing credentials: 'include'.

"It works locally but not deployed." Environment variables, HTTPS vs HTTP, a reverse proxy stripping or rewriting headers, different CORS origins, database connectivity, or a load balancer timeout shorter than your request.

Intermittent failures. These are the hard ones, and the causes are a short list: a timeout near the boundary of a slow dependency; only one instance in a pool misconfigured; a race condition; rate limiting kicking in under load; connection pool exhaustion; or a cache serving stale data. Correlation IDs and per-request latency logs are what make these findable — which is why Part 11.6 isn't optional.

9.2 The tools

curl -v (ground truth for what's on the wire), the browser Network tab (with "Copy as cURL" to reproduce a browser request in a terminal — an underrated trick), a GUI client for saved collections, jq for slicing JSON on the command line, and an HTTP-aware proxy (mitmproxy, Charles) when you need to see traffic from a client you don't control.

Internals: What Actually Happens on the Wire
TAG ADVANCED★ INTERVIEW GOLD

Return here after Part 8. This upgrades Part 3's model to mechanism.

10.1 The full journey of one API call

GET https://api.example.com/v1/books/42:

  1. DNS resolution. api.example.com → an IP address, via a cascade of caches (browser/OS/resolver) up to the authoritative nameserver. Cached per its TTL, so a stale DNS cache is a real failure mode after an IP change.
  1. TCP connection. A three-way handshake (SYN, SYN-ACK, ACK) — one full round trip before any data moves.
  1. TLS handshake. Certificate exchange and key agreement — another 1–2 round trips (one in TLS 1.3). This is why https has a fixed startup cost and why connection reuse matters so much: creating a new connection per request can easily triple your latency.
  1. The HTTP request is serialized and sent — exactly the text from Part 3.1.
  1. Intermediaries may handle it before the origin ever sees it: a CDN edge (which may serve it from cache and stop here), a load balancer choosing a backend, an API gateway doing auth and rate limiting, a reverse proxy terminating TLS. This is REST's *layered system* constraint in action — and each hop can add its own timeout, header rewriting, and failure mode, which is why "works locally, fails deployed" is so common.
  1. The application routes the path to a handler, authenticates, authorizes, validates, queries the database, serializes a response.
  1. The response travels back, possibly compressed (Content-Encoding: gzip) and possibly cached at each layer according to its Cache-Control.
  1. The connection is kept alive for reuse rather than closed (default since HTTP/1.1).

Every one of those steps is a place latency and failure can originate. Knowing the list is what lets you answer "why is this endpoint slow?" with measurement instead of guesswork — and the answer is frequently DNS, TLS, or a proxy timeout rather than your code.

10.2 HTTP versions and why they changed [DEEP for interviews]

VersionTransportKey changeWhat it fixed
HTTP/1.0TCP, one request per connection—Every request paid a full handshake
HTTP/1.1 (1997)TCP, persistent connectionsKeep-alive, chunked transfer, Host header (enabling virtual hosting), caching headersConnection reuse. But head-of-line blocking: responses must come back in order on a connection, so one slow response stalls those behind it. Browsers worked around this with ~6 parallel connections per host — which is why "bundle your files" and "domain sharding" were performance advice
HTTP/2 (2015)TCP, binary framingMultiplexing many concurrent streams over one connection, header compression (HPACK), server push (now largely abandoned)Application-level head-of-line blocking. But TCP-level blocking remains: one lost packet stalls every stream, since TCP guarantees ordered delivery
HTTP/3 (2022)QUIC over UDPStreams are independent at the transport level; faster handshake (TLS built in); connection migration across networksTCP head-of-line blocking, and mobile network switching

The through-line: each version attacked the round-trip and blocking costs of the previous one. Practical consequence for you: many old performance practices (bundling everything into one file, sharding across domains) are counterproductive on HTTP/2 and HTTP/3. And connection reuse remains the biggest single client-side win — use a persistent HTTP client (a requests.Session, a shared httpx.Client, a keep-alive agent) rather than creating a new connection per call. This is a very common and very cheap production fix.

10.3 Where the time actually goes [DEEP as a diagnostic habit]

For a typical API call, latency decomposes roughly into: DNS + TCP + TLS (fixed startup cost, avoidable through reuse), network transit (bounded by geography and the speed of light — roughly 30ms round trip within a continent, 200ms+ across the world), server processing, and response transfer.

Two consequences that shape design far more than code optimization:

  • Round trips dominate. One request returning 100 items beats 100 requests returning one item, almost regardless of payload size. This is precisely the over-fetching/under-fetching pressure that produced GraphQL (Part 12).
  • Geography is physics. You cannot optimize your way past a 200ms round trip; you can only avoid making the round trip, which is what caching and CDNs do. This is why REST's cacheability constraint is described as the biggest reason the web scales.

Production: Caching, Idempotency, Rate Limits, Security, Observability

11.1 Caching [DEEP — the highest-leverage thing most APIs ignore]

A cache hit is infinitely faster than any optimization, because the request doesn't happen.

http
Cache-Control: public, max-age=300           # anyone may cache for 5 minutes
Cache-Control: private, max-age=60           # only the client, not shared proxies
Cache-Control: no-store                      # never cache (auth responses, personal data)
Cache-Control: no-cache                      # cache, but always revalidate before use
ETag: "a3f9c2"                               # opaque version of this representation

Conditional requests are the mechanism that saves bandwidth without risking staleness:

http
GET /books/42
If-None-Match: "a3f9c2"

HTTP/1.1 304 Not Modified          ← no body at all; the client reuses what it has

Getting this right requires deciding, per endpoint: is this response public or per-user (private vs public — getting this wrong can leak one user's data to another via a shared cache, a serious bug), how stale may it be, and can I generate a cheap ETag? Anything authenticated should be private at minimum, and anything sensitive no-store.

11.2 Idempotency keys [DEEP — directly from Idea 2]

POST isn't idempotent, but retries are unavoidable. The standard solution, popularized by Stripe:

http
POST /payments
Idempotency-Key: 7f3c9a12-4b8e-4d21-9f77-2c1e5a9b8d34

{"amount": 1299, "currency": "INR"}

The server stores the key with the result of the first successful request. A repeat of the same key returns the original response instead of performing the action again. Implementation notes: the client generates the key (typically a UUID per logical operation, kept across retries), the server keeps them for at least 24 hours, and a concurrent duplicate should return 409 rather than racing.

Use this on any create-or-charge operation where duplication is harmful. This one mechanism is the difference between an API that's safe to retry and one that double-charges customers.

11.3 Optimistic concurrency [DEEP]

Two users load the same record and both save. Without protection, the second silently overwrites the first — the lost update problem, the same one covered in the SQL curriculum's isolation section, appearing here at the API layer.

http
GET /books/42          →  ETag: "v7"
PATCH /books/42
If-Match: "v7"                             # "only if it's still version 7"

HTTP/1.1 412 Precondition Failed           # someone else changed it; re-fetch and retry

This is a small amount of work that converts silent data loss into an explicit, handleable conflict.

11.4 Rate limiting [RECOGNIZE]

Protects you from abuse, accidental loops, and one noisy client degrading everyone else.

http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
RateLimit-Limit: 1000
RateLimit-Remaining: 0
RateLimit-Reset: 1754902800

Algorithms in increasing sophistication: fixed window (simple, allows bursts at boundaries), sliding window, token bucket (the usual choice — allows controlled bursts while limiting the sustained rate), leaky bucket. Limit per API key or user, not per IP where possible (shared NATs mean per-IP limits punish innocent users). Always return the headers so well-behaved clients can self-regulate rather than guess.

11.6 Observability [DEEP as a practice]

You cannot operate what you can't see. The minimum viable set:

  • Structured logs (JSON) with a correlation/request ID on every line, propagated to downstream calls via a header. This is what makes a user's bug report traceable in seconds.
  • Metrics per endpoint: request rate, error rate by status class, and latency as percentiles (p50, p95, p99 — never averages, which hide the tail where users actually suffer).
  • Health endpoints: a shallow /health for load balancer liveness, and optionally a deeper readiness check that verifies dependencies.
  • Distributed tracing for multi-service calls, so you can see which hop consumed the time. [ADVANCED]
  • Never log tokens, passwords, card numbers, or personal data. Redact at the logging layer, because someone will eventually log a whole request body.

When REST Is and Isn't the Right Choice
TAG DEEP

Being able to argue against your default is a mark of real understanding.

REST over HTTP is a strong default when: you're building a public or partner-facing API; clients are diverse and you don't control their deployment; the domain is naturally resource-shaped (CRUD over entities); caching is valuable; you want the ecosystem — browsers, curl, proxies, CDNs, OpenAPI tooling — to work with no special client.

Consider an alternative when:

AlternativeBetter whenTrade-off you accept
GraphQLClients need widely varying subsets of a complex graph; mobile clients suffering over-fetching and N+1 round trips; many frontend teams consuming one backendHTTP caching largely stops working (everything is one POST to /graphql); server-side complexity; query cost/depth limiting becomes mandatory or clients can DoS you; harder rate limiting
gRPCInternal service-to-service traffic where you control both ends; high throughput; strict schemas and generated clients; streamingNot natively callable from browsers (needs a proxy); binary payloads are harder to debug by hand; tighter coupling via generated stubs — the coupling REST was designed to avoid, which is fine *inside* a boundary you control
WebSocketsGenuinely bidirectional, low-latency, persistent interaction: chat, multiplayer, collaborative editing, live tradingStateful connections break REST's scaling story; you must handle reconnection, backpressure, and sticky routing yourself
Server-Sent Events (SSE)One-way server→client streaming: notifications, progress, live dashboardsSimpler than WebSockets and works over plain HTTP; one direction only
Message queues / events (Kafka, SQS, RabbitMQ)Asynchronous work, decoupled producers and consumers, retries, fan-out, guaranteed eventual processingNo immediate response; you inherit an entire distributed-systems problem set (ordering, duplicates, dead letters)
WebhooksYou need to notify *someone else's* server of an eventYou must handle retries, signing, and the fact that receivers are unreliable; receivers must handle duplicates
Plain RPC over HTTPGenuinely action-oriented internal APIs where resource modelling is a contortionYou lose caching and uniform-interface benefits — often an honest trade

And REST's real weaknesses, stated plainly rather than defended: it's chatty (fetching a screen's worth of data can take several round trips, which is exactly the pain GraphQL was created for); over- and under-fetching are structural, since one representation must serve all clients; there's no standard for filtering, pagination, error format, or versioning, so every API invents its own dialect; partial updates are genuinely awkward (PATCH semantics are underspecified — JSON Patch and JSON Merge Patch both exist and neither won); and HATEOAS, the constraint that would make REST self-describing and truly evolvable, is almost universally skipped, so clients hard-code URLs after all.

A pragmatic industry pattern worth knowing: REST at the public edge, gRPC or events internally. You get evolvability and ecosystem support where you don't control clients, and efficiency where you do.

Milestones and Self-Assessment

Milestone 1 — Model (Parts 1–2). Pass: the five checkpoint questions in Part 2, unaided; name Fielding's constraints and what statelessness buys.

Milestone 6 — Depth (Parts 9–12). Pass: debug an unfamiliar failing integration using the Part 9 tree; deliver the Part 10.1 narration; implement idempotency keys and If-Match and explain what each prevents; argue for GraphQL or gRPC over REST in a specific scenario and name what you'd lose.

A realistic pace at ~1 focused hour per day: M1 days 1–2, M2 days 3–5, M3 days 6–11, M4 days 12–16, M5 days 17–26, M6 days 27–33.

The exercises are the curriculum. In particular, do not skip running curl -v by hand early on — almost everyone who finds APIs confusing has only ever seen them through a library that hid the request, and seeing the raw exchange once dissolves most of the confusion permanently.
