01

Where HTML & CSS Came From

TAG DEEP

You cannot understand why CSS behaves so strangely without knowing what it was designed for. Almost every "weird" behaviour is a deliberate decision made for a document, not an app.

The lineage

YearWhat happenedWhy it still affects you
1989–91Tim Berners-Lee, at CERN, invents HTML to share physics papers between researchersHTML's native shape is a *document*: headings, paragraphs, lists, links. Not screens, not components. Every fight you have with CSS layout is a fight against a document format doing app work
1993–95Mosaic, then Netscape. Browsers compete by inventing presentational tags: <font>, <center>, <blink>, plus layout-by-<table>Presentation and content got tangled. Changing a site's font meant editing every page. This pain is *the reason CSS exists*
1994Håkon Wium Lie proposes Cascading Style Sheets; CSS1 ships 1996The word "cascading" is the core idea: many sources of style (browser default, author, user) merge by rules, rather than one winning outright
1998–2005CSS2, then the browser wars and IE6's near-monopoly. Standards support is inconsistent for a decadeWhy the "hacks era" existed, and why float-based layout — a property invented for *wrapping text around an image* — became the layout system for 15 years
2004–08Mozilla, Opera, Apple form WHATWG because W3C was pushing XHTML2 (a clean break that ignored real-world pages). WHATWG writes HTML5 insteadThe decisive principle of the web: don't break existing pages. Browsers must render 1996 HTML forever. This is why HTML is famously forgiving and why nothing is ever removed
2014HTML5 finalized; semantic elements, forms, media, canvasThe "living standard" model — HTML has no versions now, it just evolves
2012–2017Flexbox and Grid ship: the first layout systems actually designed for layoutThe single biggest change in CSS history. Everything you read pre-2017 (float grids, clearfix, 12-column frameworks) is obsolete
2016–nowCustom properties, clamp(), :has(), container queries, cascade layers, :is(), subgrid"Modern CSS" isn't a style — it's that the platform now natively does what needed JS or preprocessors for a decade

The three ideas actually invented here

  1. Separation of content from presentation. HTML says what a thing *is*; CSS says how it *looks*. This is why an <h1> styled to look small is still a heading to Google and to a screen reader — and why "make it look like X" is never a reason to pick a tag.
  2. The cascade. Style comes from multiple stakeholders (browser defaults, the author, the user's own preferences and accessibility settings) and merges predictably. CSS is not a rendering command list; it's a *negotiation*, and specificity is the negotiation's arithmetic.
  3. Graceful degradation as a design axiom. An unknown tag renders as inline text; an unknown CSS property is silently dropped. Nothing errors. This is why the web scales across 30 years of browsers — and why your typo fails *silently* instead of shouting, which is the single most annoying thing about learning CSS.

The thing worth saying in an interview

CSS is often called badly designed. The more accurate claim: CSS was correctly designed for a problem that changed. It was built to style flowing documents on unknown screen sizes with unknown fonts, where the author does not control the viewport. That constraint — *the author cannot know the canvas* — is why CSS is declarative, why boxes size themselves from content, and why "vertical centering was hard" for 20 years. Flexbox and Grid didn't fix a broken language; they added the missing primitive for a use case (application layout) that didn't exist in 1996.

02

The Core Mental Model

TAG DEEP

Four ideas. Everything else in this document is detail on top of these.

Idea 1: The document is a tree, and the browser builds it before it styles it

Your HTML text is parsed into the DOM — a tree of nodes. Your CSS is parsed into the CSSOM. The browser combines them into a render tree of only the visible boxes, then computes layout (where every box goes), then paints pixels, then composites layers.

terminal
HTML text ──parse──▶ DOM  ┐
                          ├──▶ Render tree ──▶ Layout ──▶ Paint ──▶ Composite
CSS text  ──parse──▶ CSSOM ┘                    (geometry)  (pixels)  (GPU)

Consequences you will rely on constantly:

  • CSS selectors match against the tree, which is why you can only style descendants and (now, with :has()) limited ancestors — not "the element before this one."
  • display: none removes a box from the render tree entirely (no geometry, no paint). visibility: hidden keeps the box in layout. opacity: 0 keeps it in layout *and* paint. Three ways to "hide" with three different costs and three different accessibility outcomes.
  • Changing geometry (width, top, font-size) forces layout recalculation — expensive. Changing only transform/opacity can skip to compositing — cheap. This one fact drives all CSS animation performance advice (Part 10).

Idea 2: Everything is a box, and the box model is the arithmetic

Every element generates at least one rectangular box: content → padding → border → margin, inside-out.

The historical trap: by default, width sets the *content* width, so padding and border are *added on top*. Set width: 200px; padding: 20px and you occupy 240px. This surprised everyone for a decade, so:

css
*, *::before, *::after { box-sizing: border-box; }

border-box makes width mean the *border-box* width — padding and border included. This single line goes at the top of every stylesheet you will ever write. Understand *why* it exists; that's the [DEEP] part. [RECOGNIZE] the syntax.

The other half of Idea 2: boxes are either block (take full available width, stack vertically) or inline (flow with text, ignore width/height and vertical margins). display changes which. Nearly all "why won't this element take a height?" confusion is an inline box being asked to behave like a block one.

Idea 3: Normal flow is a layout system, and it's usually right

Before you position anything, the browser already lays out your document: blocks stack top to bottom filling their parent's width, inline content flows left to right and wraps. This is normal flow, and it is *responsive by default* — that's what a document format buys you.

The mental discipline: fight flow only when you have a reason. Most beginner CSS is a pile of position: absolute, fixed pixel widths, and float fixing problems created by the previous fix. The professional move is to stay in flow, and reach for flexbox/grid to arrange *within* flow.

Corollary that explains a lot of pain: height and width are not symmetric. A block box's width is given by its parent (fill available); its height is given by its content (fit content). That asymmetry is deliberate — pages scroll vertically, so vertical space is unbounded and horizontal space is fixed. It's why width: 50% always works and height: 50% often silently does nothing (percentage heights need a definite parent height to resolve against).

Idea 4: The cascade decides who wins, in a fixed order

When several rules set the same property on the same element, the winner is decided by walking these in order and stopping at the first tiebreak:

  1. Origin & importance — browser defaults < author styles < author !important < user !important
  2. Cascade layers (@layer) — later layers beat earlier ones [ADVANCED]
  3. Specificity — counted as three numbers: (IDs, classes/attributes/pseudo-classes, elements). #nav .item a = (1,1,1). Compared left to right; a single ID beats any number of classes
  4. Source order — last one wins

Then, separately: inheritance. Some properties (color, font-*, line-height) inherit to descendants; most (border, padding, background) don't. An element with no matching rule for an inheritable property takes its parent's *computed* value.

Why the design matters: this is what "cascading" means. The browser's defaults, your stylesheet, and the user's accessibility overrides all coexist, and specificity is the referee. Understanding this is what separates "I add !important until it works" from "I know exactly which rule is winning and why."

Checkpoint — before Part 3

Answer without looking:

  1. You set height: 100% on a <div> and nothing happens. Give the mechanical reason.
  2. #sidebar p { color: red } and .warning.big.urgent.critical { color: blue } both match a paragraph. Which wins, and why is that arguably a bad design in your codebase?
  3. Why does display: none cost less to animate away from than opacity: 0? (Trick question — answer in terms of the pipeline.)
  4. Why is HTML forgiving of a missing closing tag but CSS silent about a misspelled property?

03

HTML as Meaning, Not Appearance

3.1 The one rule [DEEP]

**Choose tags by what the content *is*, never by how it looks.** Appearance is CSS's job entirely. This isn't purity — it has four concrete payoffs: screen readers navigate by structure, search engines rank by structure, browsers give you free behaviour (a <button> is focusable, keyboard-activatable, and announced as a button; a styled <div> is none of those and you'd have to reimplement all three), and future restyling doesn't require re-tagging.

3.2 The set that matters [RECOGNIZE, with [DEEP] on the concept]

CategoryElementsThe point
Document structureheader, nav, main, section, article, aside, footerThese are landmarks; assistive tech jumps between them. Exactly one <main> per page
Headingsh1–h6An outline, not sizes. Never skip levels for visual reasons. A screen-reader user's primary navigation is the heading list
Textp, ul/ol/li, strong, em, blockquote, code, timestrong/em carry *meaning* (importance/stress); b/i are purely visual and mostly legacy
Links vs buttonsa[href] navigates; button actsGetting this wrong is the most common accessibility bug on the web
Mediaimg[alt], picture, video, svgalt is mandatory. Empty alt="" is correct for purely decorative images — that's a real distinction, not a cop-out
Formsform, label[for], input, select, textarea, fieldset, buttonSee below
Tablestable, thead, tbody, th[scope], captionStill correct — for *tabular data*. Never for layout
Genericdiv (block), span (inline)Legitimate when there is genuinely no semantic meaning, only a styling hook. Not a sin — just not a default

3.3 Forms deserve their own section [DEEP]

Forms are where HTML gives you the most for free and where most hand-rolled UIs regress:

html
<form>
  <label for="email">Work email</label>
  <input id="email" name="email" type="email" required
         autocomplete="email" inputmode="email">

  <label for="qty">Quantity</label>
  <input id="qty" name="qty" type="number" min="1" max="99">

  <button type="submit">Create account</button>
</form>

What you got without writing JS: keyboard support, browser autofill, mobile keyboards matched to the input type, native validation, password-manager integration, and a label that both describes the field to a screen reader *and* expands its click target. The for/id pairing is the single highest-value line in the snippet.

Common mistakes: <div onclick> instead of <button>; placeholder used *as* a label (it disappears on typing and fails contrast); type="submit" omitted so Enter doesn't submit; and inputs with no name, which silently submit nothing.

3.4 Accessibility is mostly a byproduct [DEEP as principle]

If you use correct elements, label your inputs, keep a sane heading outline, write real alt text, and never remove focus outlines without replacing them, you have most of WCAG for free. ARIA attributes are for the cases where no native element expresses what you're building — and the first rule of ARIA is not to use ARIA if a native element exists. Bad ARIA is worse than none.

3.5 Exercise

Take a page you've shipped in one of your React projects. Strip every class attribute and view it with CSS disabled. If the resulting bare document doesn't read as a sensible outline — heading levels in order, nav distinguishable from content, forms labelled — your HTML is doing no semantic work, and everything downstream (SEO, a11y, and your own ability to style it) is harder than it needs to be.

04

CSS Fundamentals: Cascade & Values

4.1 Selectors [RECOGNIZE the list, DEEP on strategy]

css
.card                    /* class — your default tool, 99% of styling */
#checkout                /* id — high specificity, avoid for styling */
button[type="submit"]    /* attribute */
.card > .title           /* direct child */
.card .title             /* any descendant */
li + li                  /* next sibling — great for "all but first" spacing */
:hover :focus-visible    /* state. focus-visible ≈ keyboard-only focus ring */
:nth-child(2n)           /* structural */
::before ::after         /* generated content (needs `content:`) */
:is(h1,h2,h3)            /* grouping, takes the highest specificity inside */
:where(h1,h2,h3)         /* grouping with ZERO specificity — ideal for resets */
.card:has(img)           /* parent selector — genuinely new power, 2023+ */

The strategy that matters more than the syntax: keep specificity low and flat. Prefer a single class. Deep selectors (.page .sidebar ul li a span) are brittle — they encode your HTML structure into your CSS, so a markup change breaks styling in a distant file. This is exactly the problem BEM, CSS Modules, and Tailwind each solve differently (Part 11).

4.2 Custom properties [DEEP — this is where modern CSS starts]

css
:root {
  --space: 8px;
  --brand: oklch(65% 0.18 250);
  --radius: 6px;
}
.card { padding: calc(var(--space) * 2); border-radius: var(--radius); }

Not just variables — they inherit and are live. A custom property set on a parent cascades to descendants, can be overridden per-component or per-media-query, and can be read and written from JS. That's why theming (dark mode, per-tenant brands) is now a CSS problem, not a build problem:

css
:root { --bg: white; --fg: #111; }
@media (prefers-color-scheme: dark) { :root { --bg: #0d1117; --fg: #e6edf3; } }
body { background: var(--bg); color: var(--fg); }

Sass variables cannot do this — they're compiled away before the browser sees them. Understanding *that* difference is the [DEEP] part.

4.3 Values and units [DEEP on the model, REFERENCE the list]

UnitRelative toUse for
pxNothing (absolute-ish)Borders, tiny fixed details
remRoot font sizeAlmost everything: type, spacing, radii. Respects user font-size preference
em*This element's* font sizeSpacing that should scale with local text (e.g. padding inside a button)
%Depends on property — width→parent width, but padding/margin *always* → parent width, even verticallyFluid widths. The vertical-percentage-uses-width quirk is a classic gotcha
chWidth of "0"Max line length for readability (~60–75ch)
vw/vhViewportFull-screen sections. Use dvh/svh on mobile — 100vh is broken by mobile browser chrome, a bug that plagued the web for years
frFree space in a gridGrid tracks only

The reason to default to rem rather than px: a user who sets a larger browser font for legibility gets a proportionally larger UI. Hardcoded px type ignores them. That is an accessibility decision disguised as a unit choice.

Modern functions you'll actually use [RECOGNIZE]: calc(), min(), max(), and above all clamp(min, preferred, max) — which replaces most media queries for sizing:

css
h1 { font-size: clamp(1.75rem, 5vw, 3.5rem); }   /* fluid, bounded, no breakpoints */

4.4 Common mistakes at this level

  • !important used as a tool rather than an emergency. It's a signal your specificity is out of control; fix the cause.
  • Styling by ID, then being unable to override it anywhere.
  • Removing outline on focus with nothing to replace it — instantly makes a site unusable by keyboard.
  • Reaching for a preprocessor for nesting and variables, both of which are now native.

05

Layout: Flow, Flexbox, Grid, Positioning

This part is the one that changes your working life. Post-2017 CSS has exactly two layout systems, and picking the right one makes most layout problems evaporate.

5.1 The choice [DEEP]

FlexboxGrid
DimensionsOne axis at a time (a row *or* a column)Two axes simultaneously
Sizing driven byContent — items size themselves, then distribute leftover spaceThe container — you define the tracks, items fill them
Use whenDistributing a variable number of items along a line: nav bars, toolbars, button rows, card internals, centeringYou need alignment in *both* directions: page shells, dashboards, card galleries, forms
Mental imageBeads on a wireGraph paper

The heuristic that resolves 90% of cases: is the number of items unknown and their arrangement essentially one-dimensional? Flex. Do you want rows AND columns to line up? Grid. They nest freely — a grid page shell whose cells contain flex rows is the most common real structure on the web.

5.2 Flexbox mental model [DEEP]

One container, one main axis (set by flex-direction), one perpendicular cross axis. Then:

css
.bar {
  display: flex;
  flex-direction: row;      /* main axis = horizontal */
  justify-content: space-between;  /* distribute along MAIN */
  align-items: center;      /* align along CROSS */
  gap: 1rem;                /* spacing — never use margins for this anymore */
  flex-wrap: wrap;          /* allow a second line */
}

The one rule everybody gets backwards: **justify-* works on the main axis, align-* on the cross axis.** Flip flex-direction to column and they swap meaning. Internalize *that*, not the property names.

On children, the shorthand worth understanding rather than copying: flex: <grow> <shrink> <basis>.

  • flex: 1 → "grow to share leftover space equally, and let me shrink" — the everyday value.
  • flex: 0 0 auto → "don't grow, don't shrink, size to content" — for things like icons that must keep their size.
  • min-width: 0 on a flex child is the fix for the notorious "long text refuses to shrink and overflows my layout" bug — flex items won't shrink below their content's minimum size unless you tell them they may.

Centering, since it's the historical punchline: display:flex; align-items:center; justify-content:center — and it now works for any content, any size, both axes. Twenty years of hacks, replaced by three lines.

5.3 Grid mental model [DEEP]

You define tracks; items land in cells.

css
.gallery {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(240px, 1fr));
  gap: 1.5rem;
}

Read that middle line closely, because it is the single most useful line in modern CSS: *make as many columns as fit, each at least 240px, sharing space equally.* That is a fully responsive card grid — with no media queries at all. Understanding minmax() + auto-fill + 1fr gives you more responsive power than any framework's grid classes.

For page shells, named areas make the intent readable:

css
.shell {
  display: grid;
  grid-template-columns: 240px 1fr;
  grid-template-areas: "sidebar header" "sidebar main";
  min-height: 100dvh;
}
.shell > nav    { grid-area: sidebar; }
.shell > header { grid-area: header; }
.shell > main   { grid-area: main; }

fr is the concept to actually understand: it's a share of *leftover* space after fixed tracks and gaps are subtracted — which is why 1fr behaves better than % (percentages don't account for gap and cause the classic 1px overflow).

5.4 Positioning [RECOGNIZE, with two [DEEP] traps]

ValueBehaviour
staticDefault; in flow
relativeIn flow, offset visually, and becomes a positioning context for absolute children
absoluteRemoved from flow; positioned against nearest positioned ancestor
fixedAgainst the viewport
stickyIn flow until it hits a scroll threshold, then pins. Needs a threshold (top: 0) and an ancestor that isn't clipping overflow

Trap 1: position: absolute with no positioned ancestor anchors to the page, not the component you meant. position: relative on the parent is the fix, and this pairing is one of the most-used idioms in CSS.

Trap 2: z-index only works on positioned (or flex/grid) items, and only within its stacking context. A child with z-index: 9999 can never escape above a sibling whose parent has a lower z-index. When z-index "doesn't work," the answer is almost always a stacking context you didn't know you created (transform, opacity < 1, filter, and will-change all create one). Part 10 explains the mechanism.

5.5 Exercises

  1. Build a nav bar: logo left, links centre, button right — with flex only, no margins for spacing.
  2. Build a responsive card grid with the auto-fill/minmax line above, then resize the window and watch the column count change without a single media query.
  3. Build a dashboard shell with a fixed sidebar and scrollable main using grid + 100dvh.
  4. Deliberately break z-index: nest a z-index: 9999 element inside a transformed parent and explain why it's still behind its uncle element.

06

Responsive & Modern CSS

6.1 The premise [DEEP]

Responsive design isn't a technique, it's an acknowledgement: you do not know the canvas. Screen size, font size, input type, colour scheme, connection speed, and language are all decided by the user. CSS was designed for exactly this uncertainty (Part 1), so the modern approach is to *let content dictate layout* rather than enumerating device sizes.

Practical consequence: breakpoints should come from your content, not from device names. "iPhone width" is a moving target and there are hundreds of devices. Resize until the layout looks wrong; put a breakpoint there.

6.2 The toolkit, best-first

  1. Intrinsic sizing, no queries at all — auto-fill/minmax, flex-wrap, clamp(), min()/max(), max-width on text containers. Most responsiveness should come from here. [DEEP]
  2. Container queries — respond to the *component's* width, not the viewport's. This is the correct model for component-based codebases like yours: a card in a sidebar and the same card in a main column should style themselves, not depend on page context. [DEEP concept, RECOGNIZE syntax]
css
.card-wrap { container-type: inline-size; }
@container (min-width: 400px) { .card { grid-template-columns: 120px 1fr; } }
  1. Media queries — still right for genuinely page-level shifts and for user preferences: [RECOGNIZE]
css
@media (min-width: 48rem) { ... }              /* mobile-first: add complexity upward */
@media (prefers-color-scheme: dark) { ... }    /* respect the OS setting */
@media (prefers-reduced-motion: reduce) { ... }/* an accessibility obligation, not a nicety */

Mobile-first (min-width) rather than desktop-first is the default because the mobile layout is usually the simpler base, so you're *adding* rules as space allows rather than undoing them.

6.3 Common mistakes

  • Fixed heights on anything containing text — text reflows at every screen size and in every language (German words are long, and your bilingual EN/HI work makes this concrete).
  • 100vh on mobile (use dvh), and pixel media queries that ignore user font scaling (use rem).
  • Hiding content on mobile with display: none and calling it responsive — it's still downloaded, and you've removed information rather than adapting it.
  • Testing only by resizing a desktop window: that never tests touch targets (min ~44px), hover-less interaction, or real device font rendering.

07

Visual Craft: Type, Colour, Motion

This part is where "technically correct" becomes "looks professional." It's mostly a small number of decisions made *systematically* instead of ad hoc.

7.1 Systems beat one-offs [DEEP as principle]

Amateur CSS picks values per element (13px here, 17px there, #4a90d9 in one place and #4b91da in another). Professional CSS defines scales once and only uses values from them:

css
:root {
  /* spacing: one 4px-based scale, nothing off-scale */
  --s1:.25rem; --s2:.5rem; --s3:.75rem; --s4:1rem; --s6:1.5rem; --s8:2rem; --s12:3rem;
  /* type: a ratio-based ramp, not arbitrary sizes */
  --t-sm:.875rem; --t-base:1rem; --t-lg:1.25rem; --t-xl:1.75rem; --t-2xl:2.5rem;
}

This is exactly what Tailwind's p-4/text-lg classes are — a design-token scale with a naming convention. Knowing that lets you read Tailwind as CSS rather than as magic, and lets you build the same discipline without it.

7.2 Typography [DEEP — highest visual ROI]

Four decisions carry most of the result: a line length of 60–75 characters (max-width: 65ch), a line height near 1.5 for body and ~1.1 for large headings, a type scale with clear jumps (not 16/17/18px), and font loading that doesn't cause invisible text (font-display: swap) or layout shift.

7.3 Colour [RECOGNIZE, one [DEEP] rule]

The [DEEP] rule is contrast: 4.5:1 for body text, 3:1 for large text and UI boundaries. Not optional, and trivially checkable in DevTools. Beyond that: define semantic tokens (--surface, --text, --border, --accent) rather than raw colours at call sites, so dark mode is a token swap. Modern colour spaces (oklch()) give perceptually even lightness steps, which is why palettes built in them look consistent while HSL ramps don't. [ADVANCED]

7.4 Motion [RECOGNIZE]

css
.btn { transition: background-color .15s ease, transform .15s ease; }
.btn:active { transform: translateY(1px); }
@media (prefers-reduced-motion: reduce) { * { transition: none !important; animation: none !important; } }

Rules: animate only transform and opacity (Part 10 explains why — everything else forces layout or paint); 150–250ms for UI feedback; motion should explain a change (where did this come from?), never decorate. And always honour prefers-reduced-motion — for some users motion causes actual nausea.

08

Real Project: A Full Responsive Page

Build this by hand, no framework, no utility classes. The point is that afterwards you'll know precisely what Tailwind or a component library is doing for you.

Spec: a product landing page with

  1. A sticky header: logo, nav, CTA (flex)
  2. A hero with fluid type (clamp) and a two-column layout that stacks on narrow screens (grid + one breakpoint)
  3. A feature card grid, responsive with no media query (auto-fill/minmax)
  4. A pricing table with a highlighted tier (grid, :has() or a class for the highlight)
  5. A real form: labelled inputs, native validation, visible focus states, error styling via :invalid / :user-invalid
  6. A footer with grouped link columns
  7. Dark mode via custom properties + prefers-color-scheme, plus a manual toggle using a data-theme attribute on <html>
  8. Zero fixed heights, zero !important, zero IDs used for styling

Definition of done: it works from 320px to 2560px; the whole page is navigable and operable by keyboard alone with a visible focus ring at every step; the heading outline is sensible with CSS disabled; every colour pair passes contrast; and there is exactly one media query and one breakpoint value in the whole file.

Then the reflection step that matters most: rebuild the *same* page with Tailwind and write down, honestly, which parts got faster and which parts got harder to reason about. You'll be making that trade-off for the rest of your career; make it with evidence.

09

Debugging Playbook

TAG DEEP

CSS debugging is systematic. Nearly every bug is one of six things, and DevTools tells you which within seconds.

The four DevTools panels that matter

PanelAnswers
Elements → StylesWhich rules match, in cascade order, with overridden values struck through. This is where "why isn't my rule applying" is *always* answered

The decision tree

My rule isn't applying. In order: (1) does the selector actually match? — check Styles; if the rule isn't listed at all, your selector is wrong, not your property. (2) Is it struck through? Something more specific won — read the winner. (3) Is it listed and not struck but still no effect? Then either the property doesn't apply to that display type (e.g. height on an inline element, justify-content on a non-flex parent) or you misspelled the value, which CSS drops silently.

There's an unexplained gap. Candidates: default margin on h1/p/ul (browser defaults, see Computed); margin collapsing between adjacent/parent-child block margins; inline-block whitespace between elements; or a line-height taller than the content. Flex/grid gap avoids most of this by design.

Something overflows horizontally. A fixed-width child, a long unbreakable string (fix: min-width: 0 on flex children, overflow-wrap: anywhere on text), an image without max-width: 100%, or 100% + padding without border-box.

z-index isn't working. Is the element positioned? Is it in the same stacking context as the thing you want to beat? Walk up the ancestors looking for transform, opacity < 1, filter, will-change, or a lower z-index — the culprit is one of those (Part 10.3).

position: sticky isn't sticking. No threshold set, or an ancestor has overflow: hidden/auto, or the parent is shorter than the sticky element's travel.

It works on desktop, breaks on mobile. 100vh, hover-only interactions, touch targets under 44px, or a viewport meta tag missing entirely.

The habit

Before searching: read Styles (what matched), read Computed (what won), read the box model (actual geometry). If you can't reproduce a bug in a minimal isolated snippet, you don't yet understand it — and reducing it is usually what reveals the cause.

10

Internals: The Rendering Pipeline

TAG ADVANCED★ INTERVIEW GOLD

Return here after Part 8. This upgrades Part 2's model to mechanism.

10.1 The pipeline, precisely

terminal
Parse HTML → DOM
Parse CSS  → CSSOM
DOM + CSSOM → Style (compute every property for every element)
            → Layout / "reflow" (geometry: size and position of every box)
            → Paint (fill pixels into layers: text, colours, shadows, borders)
            → Composite (assemble layers, often on the GPU)

The performance rule falls straight out of this: the later in the pipeline your change starts, the cheaper it is. Changing width or font-size invalidates Layout and everything after it. Changing background-color skips Layout but repaints. Changing transform or opacity on a composited layer can skip both and only recomposite. That is the entire reason "animate transform and opacity, not top/left/width" is universal advice — not superstition, pipeline arithmetic.

10.2 Layout thrash [ADVANCED]

Layout is normally batched until the frame ends. But reading a geometry property (offsetHeight, getBoundingClientRect(), scrollTop) forces the browser to flush pending layout *now* so it can answer you. Alternating write → read → write → read in a JS loop forces a synchronous layout every iteration — "layout thrashing," a classic cause of jank. Fix: batch all reads, then all writes.

This is the highest-value CSS internals fact for a JS developer, and it's the bridge to the JavaScript curriculum's performance section.

10.3 Stacking contexts and containing blocks [ADVANCED, explains two big mysteries]

  • A stacking context is a self-contained z-ordering scope. Created by the root element, any positioned element with a z-index, and — surprisingly — opacity < 1, transform, filter, will-change, isolation: isolate. Children can only order *within* their context, never across it. This is the mechanical answer to every "z-index: 9999 doesn't work" question.
  • A containing block is the rectangle an element's percentages and offsets resolve against: normally the parent's content box, but for absolute it's the nearest positioned ancestor's padding box, and for fixed it's the viewport — *unless* an ancestor has transform/filter/will-change, which makes *it* the containing block instead. That last exception is why "my fixed header stopped being fixed" happens.

10.4 Why the parser blocks [ADVANCED]

CSS is render-blocking by design: rendering with unstyled content then restyling would flash. Classic <script> is parser-blocking because it might document.write. Hence: stylesheets in <head>, scripts with defer (or at the end of body), and critical CSS inlined for first paint. Every "put your scripts at the bottom" rule is downstream of this one design decision.

10.5 The interview-grade narration

*"The browser streams HTML into a DOM while fetching and parsing CSS into a CSSOM. Those combine to compute styles for every element, which feeds layout — computing the geometry of every box — then paint, then composite. Style and layout are the expensive phases, so cheap animations are the ones that only touch compositing: transform and opacity. Reading layout properties from JS mid-mutation forces an early synchronous layout, which is where jank usually comes from."*

11.2 Architecture: the real trade-off [DEEP — this is a senior conversation]



Every CSS methodology exists to solve one problem: CSS is globally scoped, so names collide and nobody can safely delete anything.

12

    
When to Hand-Write CSS and When Not To

    
TAG DEEP

    

  


  
Hand-write / own the CSS when: it's a marketing or landing page where visual distinctiveness is the product; you're building a design system others consume; performance budget is tight; or the site is small enough that a build step is overhead.



Reach for a utility framework when: an app UI with many similar components, a team that needs consistency without a design-system owner, and you value velocity over markup readability. (This is your situation on most of your side projects, and it's a defensible default — as long as you can read the CSS underneath, which is what this curriculum is for.)



Reach for a component library (shadcn/ui, Radix, Mantine) when: you need accessible interactive primitives — combobox, dialog, date picker, menu. Building an accessible dialog or listbox correctly from scratch is genuinely hard (focus trapping, ARIA state, keyboard model, screen-reader announcements) and is almost never worth doing yourself.



Don't write CSS at all when: the deliverable is a document (use Markdown), an email (a different, hostile subset of CSS — use a tested template), or a PDF/report where a document tool is the right output.



And the honest limitations: CSS still has no proper parent selector for arbitrary conditions (:has() is close but not complete), no native masonry (in progress), and styling native form controls (select, date inputs, file inputs) remains inconsistent — those are the three places where you'll legitimately need JS or a library rather than CSS skill.
