Where Python Came From
TAG DEEP

Python's design is unusually *intentional*, and knowing the intent explains why it looks the way it does.

The lineage

Dec 1989Guido van Rossum starts it as a Christmas-break project at CWI (Amsterdam), as a successor to ABC — a teaching language he admired but found limitedABC gave Python its readability obsession, indentation-as-syntax, and high-level built-in types. Python was designed to be *read*, from day one

The three ideas actually invented (or chosen) here

  1. Readability as a language-level constraint. Indentation *is* syntax — you cannot write badly-formatted Python. That was a deliberate bet that code is read far more often than written, and it's why Python became the default teaching and scripting language.
  1. One obvious way. Deliberately fewer features and idioms than Perl or C++. This is why "Pythonic" is a meaningful word: the community holds that there's usually a right way, and follows PEP 8 near-universally.
  1. Glue, not engine. Python's biggest win — scientific computing and AI — came from being pleasant to write *around* fast C libraries. numpy, pandas, torch: all C/C++/CUDA underneath. Understanding this reframes "Python is slow" into "Python is slow at loops and fast at orchestrating vectorized C" — which is precisely the lesson you need for your pandas work: the loop you write in Python is the bottleneck; the operation you hand to pandas is not.

The framing that reads senior

*"Python optimized for programmer time over machine time, and for reading over writing. Its dominance in data and AI isn't about performance — it's that it's the most pleasant available interface to fast native code. And unlike JavaScript, it was willing to break backward compatibility to fix its mistakes, which cost the ecosystem twelve painful years but left a cleaner language."*

02
The Core Mental Model
TAG DEEP

Five ideas. If you get Idea 1 and 2, most Python bugs become predictable.

Idea 1: Everything is an object, and names are labels — not boxes

This is *the* Python model, and it differs from how most people first imagine variables.

A variable is not a container holding a value. It is a name bound to an object. Assignment binds a name; it never copies.

python
a = [1, 2, 3]
b = a            # b is another NAME for the SAME list object
b.append(4)
a                # [1, 2, 3, 4]

x = 5
y = x            # both name the same int object
y = 6            # rebinds y to a DIFFERENT object; x is untouched

Why both behave "differently": nothing about assignment differed. What differed is mutability — you can change a list in place, so both names see the change; you cannot change an int in place, so y = 6 had to create/point to a new object.

Everything is an object, including functions, classes, and modules — so they can be passed around, stored in lists, and given attributes. id(obj) shows identity; is compares identity while == compares value. (a is b for small ints and short strings can be surprisingly True due to interning — an implementation detail, never rely on it.)

Idea 2: Mutable vs immutable is the dividing line for all surprising behaviour

ImmutableMutable
int, float, str, bytes, tuple, frozenset, bool, Nonelist, dict, set, most class instances, bytearray

Three consequences you will hit for real:

python
# 1. The mutable default argument — the most famous Python trap
def add(item, target=[]):        # this list is created ONCE, at definition
    target.append(item); return target
add(1); add(2)                   # [1, 2]  ← shared across calls!
def add(item, target=None):      # the fix
    target = [] if target is None else target

# 2. Functions can mutate your arguments (pass-by-object-reference)
def clean(rows): rows.sort()     # caller's list is now reordered

# 3. Copies are shallow by default
import copy
shallow = original.copy()        # nested objects still shared
deep = copy.deepcopy(original)   # fully independent

Only immutable objects can be dict keys or set members — because hashing requires the value not to change. That's the whole reason tuples exist alongside lists.

Idea 3: Iteration is a protocol, and laziness is everywhere

for x in thing does not need a list. It calls iter(thing) to get an iterator, then next() repeatedly until StopIteration. Anything implementing that protocol is iterable — files, dict views, generators, database cursors, custom classes.

python
with open('big.csv') as f:        # a file IS an iterator of lines
    for line in f:               # streams, never loads the whole file
        process(line)

This is why Python handles data larger than memory gracefully, and why range(10_000_000) costs nothing (it computes on demand rather than building a list). Generators (Part 4) are how you write your own lazy pipelines — directly relevant to any ETL work.

Idea 4: Scope is LEGB, and assignment creates a local

Name lookup order: Local → Enclosing → Global → Builtins.

The rule that trips everyone: assigning to a name anywhere in a function makes it local for the entire function, even before the assignment line.

python
count = 0
def bump():
    count += 1        # UnboundLocalError — `count` is local because it's assigned here
def bump_ok():
    global count      # explicit, and usually a design smell
    count += 1

Preferred fix: don't mutate globals — return values instead. nonlocal exists for closures. Note the philosophy: Python makes you *say* you're reaching outward, matching "explicit is better than implicit."

Idea 5: Duck typing — behaviour matters, not type

Python doesn't check what something *is*; it tries what you asked and fails if unsupported. "If it quacks like a duck." Consequence: functions work with anything supporting the needed operations — a real strength for composition. Also why try/except (EAFP: easier to ask forgiveness than permission) is idiomatic where other languages check types first.

Type hints (Part 11) don't change this — the runtime ignores them entirely. They're for tooling and for humans.

03
Built-in Data Types and When to Use Each

3.1 The four workhorses [DEEP — the trade-offs, not the methods]

TypeOrderedMutableLookup costUse when
listYesYesO(n) search, O(1) indexOrdered sequence you'll modify; the default collection
tupleYesNoO(n) searchFixed records ("a row"), dict keys, safe returns of multiple values
dictInsertion order (3.7+)YesO(1) by keyLookups by key, grouping, counting, JSON-shaped data
setNoYesO(1) membershipUniqueness, membership tests, set algebra (diffs between two ID lists)

The single most valuable performance instinct in Python: x in some_list is O(n); x in some_set is O(1). Turning a list into a set before a loop of membership checks converts an accidental O(n²) into O(n). This is the most common real speedup in data-cleaning scripts, and it's the kind of thing that turns a 40-minute job into 4 seconds.

3.2 Strings [DEEP on immutability + Unicode]

Immutable — every "modification" creates a new string. So building a string in a loop with += is O(n²); use ''.join(parts). Text is str (Unicode code points); bytes are bytes. encode() goes str→bytes, decode() goes bytes→str. This distinction *is* the Python 3 break (Part 1), and it's why you must specify encoding='utf-8' when reading files — a UnicodeDecodeError on a client CSV is the single most common data-work error in India-facing work with mixed-encoding exports.

f-strings are the modern default: f"{name}: {total:,.2f}" — and f"{value=}" for debugging.

3.3 Comprehensions [DEEP — the Pythonic transformation idiom]

python
opens   = [c['id'] for c in cases if c['status'] == 'open']      # list
by_id   = {c['id']: c for c in cases}                            # dict
courts  = {c['court'] for c in cases}                            # set
lazy    = (expensive(c) for c in cases)                          # GENERATOR — nothing runs yet

Read these as SQL, since that's your native language: [expr for row in table if cond] is SELECT expr FROM table WHERE cond. Prefer comprehensions over map/filter (more readable, and Guido's own preference). Stop at two levels of nesting — beyond that, write a loop or a generator function; clarity wins.

3.4 The standard library pieces that carry real work [RECOGNIZE]

collections.Counter (frequency counts in one line), defaultdict (grouping without key checks), pathlib.Path (path handling that isn't string surgery), datetime/zoneinfo (always store UTC, convert at the edges), decimal.Decimal (money — never float, same lesson as JS), itertools (groupby, chain, islice, batched), json, csv, re, dataclasses, enum, logging.

04
Functions, Closures, Decorators, Generators

4.1 Parameters, properly [DEEP]

python
def fetch(table, *cols, limit=100, offset=0, **filters):
    ...
fetch('cases', 'id', 'court', limit=50, status='open')

*args collects extra positionals into a tuple; **kwargs collects extra keywords into a dict. Keyword-only parameters (after *) are a design tool: they force call sites to be self-documenting, which matters for functions with several similar arguments. Type hints belong here (Part 11), and the mutable-default trap from Idea 2 lives here.

4.2 Closures [DEEP]

Same mechanism as JavaScript: a nested function retains access to the enclosing scope's names.

python
def make_validator(required):
    def validate(row):
        return [f for f in required if not row.get(f)]   # `required` retained
    return validate
check = make_validator(['case_no', 'court'])

Python's version of the classic closure bug is late binding: closures capture the *name*, not the value at creation time.

python
fns = [lambda: i for i in range(3)]
[f() for f in fns]              # [2, 2, 2]  — all see the final i
fns = [lambda i=i: i for i in range(3)]   # bind at definition → [0, 1, 2]

4.3 Decorators [DEEP concept, RECOGNIZE syntax]

A decorator is a function that takes a function and returns a replacement. @ is just sugar: f = deco(f).

python
import functools, time, logging

def timed(fn):
    @functools.wraps(fn)                     # preserve __name__, docstring
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            logging.info("%s took %.2fs", fn.__name__, time.perf_counter() - t0)
    return wrapper

@timed
def load_cases(path): ...

Why they exist: cross-cutting concerns — timing, logging, retries, caching, auth, transactions — that you don't want duplicated in every function body. Once you see this, FastAPI's @app.get(...), pytest's @fixture, and @functools.lru_cache all stop being magic and become "a function wrapping my function." That single realization is worth the whole section, and it's a strong interview answer.

4.4 Generators [DEEP — the ETL tool]

A function with yield returns a generator: it produces values lazily, suspending and resuming, holding one item in memory at a time.

python
def read_rows(path):
    with open(path, encoding='utf-8') as f:
        for line in f:
            yield parse(line)                      # one row at a time

def valid(rows):
    for r in rows:
        if r['amount'] > 0: yield r

def enriched(rows):
    for r in rows:
        yield {**r, 'gst': r['amount'] * 0.18}

for row in enriched(valid(read_rows('huge.csv'))):  # a streaming pipeline
    write(row)                                       # constant memory, any file size

That composition is the correct shape for any ETL work, and it's the strongest argument for understanding the iteration protocol from Idea 3. Compare with the pandas approach: pandas loads everything into memory but vectorizes the operations. Knowing when to stream (huge files, row-independent logic) versus vectorize (fits in memory, columnar math) is a real engineering judgment — and one that will come up when you talk about data pipelines in a BA/technical interview.

05
Objects and the Data Model

5.1 Classes when they're warranted [DEEP as judgment]

Python does not require classes. A module of functions is often better. Use a class when you have state plus behaviour that belong together and multiple instances. Don't use one as a namespace for stateless functions — that's a Java habit, and un-Pythonic.

python
from dataclasses import dataclass, field
from decimal import Decimal

@dataclass
class Invoice:
    number: str
    amount: Decimal
    items: list[str] = field(default_factory=list)   # ← Idea 2, enforced by dataclasses
    def with_gst(self) -> Decimal:
        return self.amount * Decimal('1.18')

@dataclass generates __init__, __repr__, and __eq__. For records — which is most of what data work needs — it removes nearly all boilerplate. Note default_factory: the dataclass API *forces* you to avoid the mutable-default trap, which tells you how common that bug is.

5.2 The data model: dunder methods are protocols [DEEP — this is Python's real secret]

Python's built-in syntax is defined in terms of methods your objects can implement. len(x) calls x.__len__(). a + b calls a.__add__(b). for x in y calls y.__iter__(). with x: calls x.__enter__()/__exit__(). x[k] calls __getitem__.

So "Pythonic" design means: implement the protocol and your object works with the whole language.

python
class CaseList:
    def __init__(self, cases): self._cases = cases
    def __len__(self):  return len(self._cases)          # len()
    def __iter__(self): return iter(self._cases)         # for, list(), unpacking
    def __getitem__(self, i): return self._cases[i]      # indexing, slicing
    def __repr__(self):  return f"CaseList({len(self)} cases)"   # debugging

That object now works in for, len(), in, comprehensions, and list() — with no inheritance. This is duck typing (Idea 5) formalized, and it's how pandas DataFrames and numpy arrays feel native. If you can explain "the data model is a set of protocols, not an inheritance hierarchy," you're ahead of most Python interviewees.

5.3 Properties, inheritance, composition [RECOGNIZE]

@property turns a method into an attribute access — so you can add validation or computation later without changing every call site. Inheritance: use it for genuine "is-a" specialization; prefer composition (holding collaborators) otherwise. abc.ABC for defining an interface contract. Python's MRO and multiple inheritance are [ADVANCED] — know that super() follows a linearized order and leave the details until needed.

06
Errors, Control Flow, Context Managers

6.1 Exceptions are normal control flow [DEEP]

In Python, exceptions are not exceptional. StopIteration ends every for loop; KeyError is how dicts report a miss. The idiom is EAFP — try it, handle failure — rather than LBYL (check first), because checking-then-acting has race conditions and reads worse.

python
try:
    row = parse(line)
except ValueError as e:                       # catch SPECIFIC exceptions
    logging.warning("skipping bad row %r: %s", line, e)
    continue
except (KeyError, TypeError):
    raise                                     # re-raise what you can't handle
else:
    save(row)                                 # ran only if no exception
finally:
    counter += 1                              # always runs

The rules that matter: never bare except: (it swallows KeyboardInterrupt and every bug you haven't thought of); catch the narrowest exception you can actually handle; and never silence an exception without logging it. raise NewError(...) from e preserves the original cause in the traceback — the difference between a debuggable error and a mystery.

Define your own for domain failures (class ValidationError(Exception)) so callers can distinguish "the data was bad" from "the network died."

6.2 Context managers [DEEP]

with guarantees cleanup even on exception — the mechanism behind file handles, DB connections and transactions, locks, and temp directories.

python
with open(src, encoding='utf-8') as f, open(dst, 'w', newline='') as out:
    ...                                       # both closed no matter what happens

from contextlib import contextmanager
@contextmanager
def timed(label):
    t0 = time.perf_counter()
    try: yield
    finally: logging.info("%s: %.2fs", label, time.perf_counter() - t0)

with timed("load"): load_cases(path)

The reason this exists rather than manual try/finally: resource leaks are invisible until production. If you're writing .close() by hand, you're writing a future bug.

6.3 Modern control flow [RECOGNIZE]

Walrus := for assign-and-test (while (chunk := f.read(8192)):), match/case for structural pattern matching on shaped data (genuinely good for parsing API responses, overkill as a switch statement), and enumerate/zip instead of index arithmetic — for i, row in enumerate(rows, start=1) is the idiomatic counted loop.

07
Modules, Packages, Environments

7.1 Imports [DEEP enough to stop the errors]

A module is a file; a package is a directory. import x binds a *module object* to a name — modules are objects too (Idea 1), and they're executed once and cached in sys.modules.

python
from pathlib import Path              # specific name — preferred
import pandas as pd                   # conventional alias
from .models import Invoice           # relative, inside a package

Never from x import * (pollutes the namespace, breaks tooling, hides origins). The if __name__ == "__main__": guard exists because importing a module *runs* it — the guard separates "run as a script" from "imported as a library," which is what lets the same file be both.

Import errors are the #1 beginner blocker, and the cause is almost always where you ran python from, not your code: Python resolves imports against sys.path, which starts with the script's directory. Running python src/main.py versus python -m src.main produces different sys.path and thus different results. Use -m for packages.

7.2 Environments [DEEP — non-negotiable hygiene]

Every project gets its own isolated interpreter and dependency set. Installing globally guarantees version conflicts between projects — the same problem Docker solves at the OS level, solved here at the language level. (Worth noting the parallel explicitly: venv is to Python packages what a container is to system libraries. Neither replaces the other, which is why Dockerized Python still uses a venv or a clean base image.)

bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip freeze > requirements.txt        # crude: pins everything including transitive deps

Modern tooling worth adopting: uv (very fast installs, resolves and locks properly) or Poetry/PDM, with dependencies declared in pyproject.toml — the current standard, replacing setup.py and loose requirements.txt. Pin versions for anything deployed.

7.3 Project layout [RECOGNIZE]

terminal
project/
  pyproject.toml          # deps, tool config (ruff, mypy, pytest), build metadata
  src/myapp/
    __init__.py
    config.py             # env-var driven settings, no secrets in code
    models.py
    pipeline.py
    cli.py
  tests/
    test_pipeline.py
  .env                    # gitignored

src/ layout prevents accidentally importing your package from the working directory instead of the installed copy — which is how "it works on my machine but not in CI" happens in Python.

Real Projects

Two projects, chosen because they're the shapes of work you'd actually be paid for and the shapes that show up in a technical BA portfolio.

8.1 Project A — a production-shaped ETL pipeline

Spec: a CLI that ingests messy tabular data and lands it in a database, correctly.

  1. Extract — read a CSV *and* an API endpoint (httpx or requests), streaming the CSV with a generator (Part 4.4), handling encoding explicitly.
  1. Validate — a schema check with clear per-row errors, using pydantic or dataclasses plus your own validators. Bad rows go to a rejects file with reasons, never silently dropped. This is your S2T-mapping instinct expressed in code.
  1. Transform — normalize dates to UTC (datetime + zoneinfo), money as Decimal, text trimmed and case-normalized, IDs deduplicated with a set.
  1. Load — upsert into Postgres (psycopg) inside a transaction with a context manager, batched — not row-by-row.
  1. Observe — logging (not print) with levels, a run summary (rows in / loaded / rejected / duration), and a non-zero exit code on failure.
  1. Configure — argparse for CLI args, env vars for credentials, nothing secret in code.
  1. Test — pytest covering validation rules and transforms with fixtures; no DB needed for those.

Definition of done: it runs on a 500MB file without exhausting memory; a malformed row can't kill the run; re-running it twice produces the same database state (idempotent); and someone else can run it from the README alone.

Then the reflection: rewrite the transform step in pandas and compare — lines of code, memory, speed, and readability. That comparison is the actual lesson about when to stream and when to vectorize.

8.2 Project B — a FastAPI service

Spec: wrap Project A's logic in an API. Routes to trigger a run, check status, and query results. Pydantic models for request/response validation. Dependency injection for the DB session. Proper status codes and error responses. Background task for the long-running job. /health. Auto-generated OpenAPI docs (which you get free — a genuinely useful thing to show a stakeholder). Then containerize it with the Docker curriculum's Part 8 Dockerfile.

Why this pairing: A teaches you data correctness, generators, errors, and the standard library; B teaches you typing in anger (FastAPI *uses* your type hints at runtime for validation, the one place annotations aren't ignored), async, and service shape. Together they're a portfolio piece that maps directly onto a technical BA / analytics-engineering conversation.

Debugging Playbook
TAG DEEP

Read the traceback correctly

Python tracebacks are printed oldest call first, error last. So read from the bottom up: the last line is the exception and message, the line above it is where it happened, and the frames above that are how you got there. Most people skim the top and miss that the answer is at the bottom.

The decision tree

ErrorWhat it actually meansFirst move
AttributeError: 'NoneType' has no attribute 'x'Something returned None — usually a function with no return, or a lookup that missedPrint/inspect the object one step earlier
KeyError / IndexErrorThe key/index isn't theredict.get(k, default); check the actual keys, don't assume the API's shape
TypeError: ... not callable / wrong arg countName shadowing (you assigned over a function), or a signature mismatchCheck what the name is bound to
UnboundLocalErrorIdea 4 — assignment made it localDon't mutate globals; pass and return
ImportError / ModuleNotFoundErrorsys.path, wrong env, or circular importConfirm the active venv; use python -m; check for a cycle
UnicodeDecodeErrorWrong encoding assumption on inputSpecify encoding=; try utf-8-sig for Excel exports with a BOM
Wrong numbers, no errorFloat arithmetic, integer division, timezone-naive datetimes, or silent coercionDecimal for money, UTC everywhere, assert your assumptions
Mysteriously shared stateIdea 2 — mutable default or an aliased objectSearch for =[]/={} in signatures; copy.deepcopy to test the hypothesis

Tools

breakpoint() drops you into pdb at that line — n next, s step in, c continue, p expr print, l list, w where. Learning six pdb commands beats a hundred print statements, and it's the habit that most speeds up debugging. Beyond that: logging with levels instead of print (you can leave it in and turn it down), pytest -x --pdb to drop into the debugger at the first failure, dis.dis(fn) when you want to see what Python actually does (Part 10), and cProfile before optimizing anything — measure, never guess, because Python performance intuitions are wrong more often than right.

Internals
TAG ADVANCED★ INTERVIEW GOLD

10.1 CPython: what running Python actually does

python script.py → the source is parsed to an AST → compiled to bytecode (cached as .pyc in __pycache__) → executed by a stack-based virtual machine loop. There's no machine-code compilation in CPython (that's PyPy's JIT, or Numba, or Cython).

python
import dis
dis.dis(lambda x: x + 1)     # see the actual bytecode instructions

This is why Python loops are slow: every operation goes through the interpreter loop with dynamic type dispatch and object allocation, where C would be a couple of instructions. And why the fix is not "write cleverer Python" but "hand the loop to C" — numpy/pandas vectorization, exactly the Part 1 glue-language point.

10.2 Memory: reference counting plus a cycle collector

CPython frees an object the moment its reference count hits zero — which is why memory is released promptly and deterministically, unlike JS's GC. A separate generational collector handles reference cycles (a.b = b; b.a = a), which counting alone can never free.

Practical consequences: hold no references you don't need (a list of 10M objects is 10M live objects); __slots__ cuts per-instance memory noticeably for many small objects [ADVANCED]; weakref for caches that shouldn't keep things alive; and "memory not released" usually means a lingering reference — a module-level cache, a closure, or an exception traceback holding frames.

10.3 The GIL, explained properly [DEEP for interviews]

The Global Interpreter Lock allows only one thread to execute Python bytecode at a time in a CPython process. Its purpose is to make reference counting thread-safe cheaply.

The consequence that actually matters:

WorkloadBound byUseWhy
Network calls, DB queries, file I/O, API requestsI/Othreading or asyncioThe GIL is *released* during I/O waits, so threads genuinely overlap
Number crunching, parsing, image processingCPUmultiprocessing (or numpy, which releases the GIL in C)Separate processes = separate GILs = real parallelism

So the accurate claim is not "Python can't do concurrency" — it's "Python threads don't give you CPU parallelism, but they do give you I/O concurrency." Being able to state exactly that, with the release-during-I/O detail, is a strong senior signal. Add the current context: 3.13 ships an experimental free-threaded build (PEP 703), so the GIL is being actively removed — a claim to make with dates attached rather than as settled fact.

10.4 asyncio's model [ADVANCED]

Same shape as JavaScript's event loop: single-threaded cooperative multitasking. await yields control back to the loop while waiting. The difference from JS is that Python's is opt-in — you must run an event loop and use async-aware libraries. Which produces the classic beginner failure: one blocking call (requests, time.sleep, heavy CPU work) inside an async function stalls the entire loop. Rule: async code must use async libraries all the way down (httpx/asyncpg, asyncio.sleep), or offload blocking work to a thread/process executor.

Choose asyncio for thousands of concurrent connections (a web service like Project B); choose threads for a few dozen blocking calls (simpler, no library rewrite); choose processes for CPU work.

11.1 Type hints [DEEP as a decision]

python
def load(path: Path, *, limit: int | None = None) -> list[Invoice]: ...

The runtime ignores these (with the notable exception of frameworks like FastAPI and pydantic, which read them deliberately). Their value is tooling: mypy/pyright catch errors before runtime, editors autocomplete accurately, and signatures document themselves. Their cost is verbosity and occasional fights with complex generics.

Pragmatic policy: annotate all function signatures at module boundaries, skip local variables where the type is obvious, and run mypy in CI. Same caveat as TypeScript — types are not runtime validation. Validate external data (API payloads, CSVs, env vars) with pydantic; annotations alone guarantee nothing about what arrives.

11.2 Testing [RECOGNIZE]

pytest: plain functions, plain assert, fixtures for setup, parametrize for table-driven cases (which will feel natural given how you think about test cases as a BA):

python
import pytest
@pytest.mark.parametrize("raw,expected", [("1,200.50", 1200.50), ("₹0", 0.0)])
def test_parse_amount(raw, expected):
    assert parse_amount(raw) == expected

Test the logic that would embarrass you if wrong: validation rules, transforms, edge cases, money and date handling. Don't chase coverage percentages; chase the cases you'd write in a UAT test plan.

11.3 Performance, in order [DEEP as discipline]

  1. Measure (cProfile, time.perf_counter) — the bottleneck is almost never where you assumed.
  1. Fix the algorithm — the set-vs-list membership fix (Part 3.1) beats every micro-optimization.
  1. Vectorize or push into C — numpy/pandas/Polars, so the loop runs in C, not the interpreter.
  1. Parallelize correctly per the GIL table (10.3).
  1. Only then reach for PyPy, Cython, or a rewrite of the hot path in another language.

11.4 Security & operational hygiene [RECOGNIZE]

Never eval/exec on input; never build SQL by string concatenation — parameterize (cur.execute("... WHERE id = %s", (id,))), which given your SQL background is the habit to carry over most strictly; secrets in env vars, never in code or git; pin dependencies and audit them (pip-audit); validate all external input; and log without leaking PII. And use ruff — one fast tool that replaces linting and formatting, and ends all style debate.

12
When Not to Use Python
TAG DEEP

Right tool when: data work, analysis, ETL, and ML (no real competition); automation and scripting; APIs and backends where developer speed beats raw throughput; glue between systems; anywhere readability and hiring matter more than milliseconds.

Wrong or questionable when:

  • CPU-bound hot loops where the work can't be vectorized or pushed to C — Go, Rust, C++, or Java will be an order of magnitude faster.
  • Hard real-time or memory-constrained systems — GC pauses, interpreter overhead, and per-object memory cost rule it out.
  • Browser frontends — you'd be fighting the platform; JS/TS is the native answer (PyScript/WASM exists but is niche).
  • Mobile apps — no first-class story.
  • Shipping a binary to non-technical users — packaging a Python app for end users is genuinely painful (PyInstaller helps and still hurts); Go's single static binary is the contrast.
  • Very large codebases without discipline — dynamic typing plus late-bound everything means refactoring is riskier than in a statically typed language. Type hints plus mypy mitigate but don't eliminate this.

Honest weaknesses worth naming in an interview: the GIL for CPU parallelism, packaging and environment management as a historically bad experience, startup time, and memory overhead per object. Being able to list those makes your enthusiasm credible rather than naive.
