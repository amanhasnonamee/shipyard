01

The Problem Docker Solves

TAG DEEPMODE READ

You cannot understand a tool without understanding the pain that created it. Docker exists because of three chronic problems in shipping software.

Problem 1: "Works on my machine"

An application is never just your code. It is:

the-real-app.sh
# your code
  + language runtime (Python 3.11, Node 20...)
  + system libraries (libpq, openssl, glibc...)
  + OS-level config (env vars, locales, file paths)
  + external services (Postgres 15, Redis 7)
  + exact versions of ALL of the above

Your laptop, your colleague's laptop, the CI server, and production each have a different combination of these. Software that works in one environment breaks in another for reasons that have nothing to do with your code. Before containers, teams wrote 40-page "setup guides" that were outdated the day they were written.

Docker's answer

Package the code and its entire environment into one artifact (an image) that runs identically everywhere.

Problem 2: Dependency conflicts on shared machines

App A needs Python 3.8 + library X v1. App B needs Python 3.12 + library X v3. Same server. Before containers you had fragile workarounds (virtualenvs solve Python packages but not system libraries; separate servers solve everything but waste money).

Docker's answer

Each app runs in its own isolated filesystem with its own dependencies. They share the machine but never see each other's files.

Problem 3: Virtual machines are too heavy

VMs solved both problems above — full isolation, reproducible environments — but at brutal cost:

Virtual MachineContainer
What's virtualizedEntire hardware → runs a full guest OSNothing — just an isolated process on the host kernel
SizeGBs (whole OS)MBs (just app + deps)
Boot timeMinutesMilliseconds
Density per hostHandfulsHundreds
Isolation strengthStrong (separate kernels)Weaker (shared kernel)
The single most common interview question in existence

This table IS the question. Understand the "why" column, not just the numbers. The reason containers are light is the entire secret of Docker: a container is not a small VM — it is a normal process that the kernel has been told to lie to. More in Part 2.

What Docker is NOT solving

  • It does not make your code faster (slight overhead, if anything).
  • It does not replace configuration management or CI/CD — it plugs into them.
  • It does not give VM-grade security isolation (shared kernel).

02

The Core Mental Model

TAG DEEPMODE READ★ MOST IMPORTANT PART

This is the most important section in the document. Everything else is detail on top of these four ideas.

Idea 1: A container is just a process

Not a VM. Not a "lightweight OS." When you run a container, the host's Linux kernel starts an ordinary process — same as running python app.py directly — but wraps it in three kernel features:

  1. Namespaces — control what the process can see. It gets its own view of the process tree (it thinks it's PID 1), its own network stack, its own hostname, its own filesystem root. Other processes on the host are invisible to it.
  2. Cgroups (control groups) — control what the process can use. Caps on CPU, memory, I/O.
  3. A layered filesystem (OverlayFS) — gives the process a private root filesystem assembled from the image's layers.
Litmus test of understanding

Run ps aux on a Linux host with a container running — you will see the container's process listed like any other. There is no "container" object in the kernel. "Container" is just the name for a process launched with these isolation features. If you internalize only one sentence from this entire curriculum, make it this one.

Consequence you'll rely on constantly

When the main process (PID 1) inside a container exits, the container stops. A container is alive exactly as long as its process is. This explains 80% of "my container keeps exiting" confusion.

Idea 2: An image is a frozen filesystem, built in layers

An image is: a stack of read-only filesystem layers (each layer = the file changes made by one Dockerfile instruction), plus metadata: what command to run, env vars, exposed ports, working directory.

Think of it as a class; containers are instances. One image → many containers, cheaply, because containers don't copy the image. Instead:

WRITABLEThis container only — all writes go heredies with docker rm
LAYER 3Your app coderead-only · SHARED
LAYER 2pip install depsread-only · SHARED
LAYER 1Ubuntu base filesread-only · SHARED
Hover or click a layer. Then press ▶ START to run the container.

Consequences that fall out of this model

  • Starting a container is instant — no copying, just add an empty writable layer on top.
  • Deleting a container deletes its writable layer. Anything written inside a container is lost when the container is removed. This is why volumes exist (Part 5).
  • Layers are cached and shared — ten images based on python:3.12 store the Python layer once.
  • Layer ordering in a Dockerfile determines build speed (Part 4's cache section).

Checkpoint — do this before Part 3

Explain, out loud or in writing, without looking:

  1. Why is a container faster to start than a VM? (Answer must involve "it's just a process" and "shared kernel.")
  2. You write a file inside a running container, then docker rm it. Where did the file go and why?
  3. Why can two containers on one host use conflicting versions of the same library?
REVEAL ANSWERS
  1. A container doesn't boot an OS — the kernel is already running. Docker just starts one more process wrapped in namespaces, so boot is milliseconds vs minutes for a full guest OS.
  2. It went into the container's writable layer (Part 2, Idea 2). docker rm deletes that layer — the file is gone forever, which is why volumes exist.
  3. Each container has its own isolated filesystem (own MNT namespace + own layers). They share the host kernel but never each other's files.

If you can't answer all three crisply, reread Part 2. Nothing later will stick without it.

Understand deeply the difference between stopped (process dead, filesystem layer still there — can restart, data intact) and removed (gone forever). Everything else here is REFERENCE.

3.3 Inspecting running containers DEEP — YOUR DEBUGGING TOOLKIT

Four commands cover 90% of all Docker debugging. Learn these cold:

terminal
$ docker logs -f web          # what the process wrote to stdout/stderr
$ docker exec -it web bash    # open a shell INSIDE the running container
$ docker inspect web          # full JSON: config, IP, mounts, state, exit code
$ docker stats                # live CPU/memory per container
Key mental model for logs

Containers don't write log files by convention — apps in containers log to stdout/stderr, and Docker captures that stream. If your app writes to /var/log/app.log inside the container, docker logs shows nothing and the file dies with the container. This convention matters when you Dockerize Django/Node in Part 8.

Key mental model for exec

It starts an additional process inside the container's existing namespaces. That's why exec dies when the container stops, and why you can't exec into a stopped container.

  2. Run docker run -it python:3.12 python — you now have a Python REPL in a container. Exit. Explain why exiting the REPL stopped the container.
  3. Run docker run -d ubuntu and explain why docker ps doesn't show it (then find it with -a and read its exit state in inspect).

04

    
Images & Dockerfiles

    
MODE HANDS-ON

    

  


  
4.1 What a Dockerfile is DEEP

  
A Dockerfile is a build script: a sequence of instructions, each producing one image layer. docker build executes it top-to-bottom, snapshotting the filesystem after each step.

  
The canonical example — read every comment:

  
Dockerfile

  
# Every image starts FROM a base image (OS files + often a runtime).
FROM python:3.12-slim

# Set working directory for all following instructions (creates it if absent)
WORKDIR /app

# Copy ONLY the dependency manifest first — deliberate, see caching below
COPY requirements.txt .

# RUN executes a command AT BUILD TIME; its filesystem changes become a layer
RUN pip install --no-cache-dir -r requirements.txt

# Now copy the rest of the source code
COPY . .

# Documentation only — does NOT publish the port (see common mistakes)
EXPOSE 8000

# What to execute AT RUN TIME when a container starts. Exactly one CMD.
CMD ["python", "manage.py", "runserver", "0.0.0.0:8000"]

  
terminal

  
$ docker build -t myapp:1.0 .     # -t = name:tag;  . = build context (dir sent to daemon)


  
4.2 The instruction set — what to know at what depth

  

    
InstructionPurposeDepth

RUN vs CMD is the classic confusion
  
RUN happens once, during docker build, and bakes its result into the image. CMD happens every time a container starts, and bakes nothing. RUN pip install ✔ ; CMD pip install ✘ (would reinstall on every start).


  
ENTRYPOINT vs CMD RECOGNIZE NOW DEEP BY INTERVIEW TIME

  
    
    
  • CMD ["python", "app.py"] — fully overridable: docker run img bash replaces it entirely.
    • 
    
  • ENTRYPOINT ["python"] + CMD ["app.py"] — ENTRYPOINT is fixed; anything after docker run img replaces only CMD (the args). Pattern for CLI-tool images.
    • 
    
  • Always prefer the JSON/"exec" form ["a","b"] over shell form a b — shell form wraps your process in /bin/sh -c, which then becomes PID 1 and swallows SIGTERM, breaking graceful shutdown. This detail is a strong interview signal.
    • 
  


  
4.3 Layer caching — the concept that makes builds fast or slow DEEP

  
Rule: each instruction's layer is reused from cache if the instruction is unchanged AND all previous layers were cache hits. For COPY, "unchanged" means the copied files' checksums are identical. First cache miss invalidates every layer after it.

  
This is why the canonical Dockerfile copies requirements.txt before the source code:

  

    
Bad orderGood order

    
      

        COPY . .
RUN pip install -r requirements.txt		
        COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .		
      

      

        → ANY code edit busts the cache and re-runs pip install (minutes)
        → code edits only re-run the cheap final COPY; pip layer stays cached (seconds)
      

    
  

  
General principle
  
Order instructions from least-frequently-changing to most-frequently-changing. This one idea is the difference between 3-second and 5-minute rebuild loops, and interviewers probe it.

  
Related RECOGNIZE: .dockerignore — like .gitignore, excludes files from the build context. Always exclude .git, node_modules, venv, __pycache__, .env. Two reasons: smaller/faster context upload, and prevents junk (or secrets) from busting COPY . .'s cache or landing in the image.


  
4.4 Image size & multi-stage builds

  
Why size matters: pull time on every deploy, disk, and attack surface (every binary in the image is exploitable surface).

  
Levers, in order of impact:

  
    
    
  1. Small base image DEEP: python:3.12 (~1GB, full Debian) vs python:3.12-slim (~150MB) vs alpine (~50MB, but musl-libc causes subtle breakage with compiled Python wheels — for Python, slim is the pragmatic default; alpine shines for Go/static binaries).
    2. 
    
  2. Multi-stage builds DEEP CONCEPT RECOGNIZE SYNTAX: build with heavy tooling, ship only the output.
    3. 
  

  
Dockerfile.multistage

  
# Stage 1: has compilers, dev headers — huge, and that's fine
FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: final image — only the artifacts cross over
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html

  
Only the final stage ships. The 1GB of node_modules and compilers never leaves your machine. Understand the why (build-time deps ≠ run-time deps); the syntax you can copy from here forever.

  
    
    
  1. Chain related RUNs (RUN apt-get update && apt-get install -y X && rm -rf /var/lib/apt/lists/*) — because layers are additive: deleting a file in a later layer doesn't shrink the image, it just hides the file. RECOGNIZE
    2. 
  


  
4.5 Tags and registries DEEP CONCEPT

  
python:3.12-slim = repository python, tag 3.12-slim. A tag is a movable pointer to an image, exactly like a Git branch name — not a version guarantee. latest is just the default tag name; it is not "newest" and it moves, which is why production pins specific tags (or digests).

  
terminal

  
$ docker pull redis:7           # registry → local
$ docker tag myapp:1.0 username/myapp:1.0
$ docker push username/myapp:1.0   # local → registry (needs docker login)

  
Full image name anatomy: registry.example.com/team/app:tag — no registry prefix means Docker Hub.

Storage

    
MODE HANDS-ON

    

  


  
5.1 The problem DEEP

  
From Idea 2: the container's writable layer dies with the container. So how does a Postgres container keep data across upgrades? Answer: mount storage that lives outside the container's layer stack.


  
5.2 The three mount types

  

    
VolumeBind mounttmpfs

    
      
WhatDocker-managed directory on host (/var/lib/docker/volumes/...)You map an explicit host path inRAM-only

How to tell them apart in -v syntax: left side with a / or . = path = bind mount; bare name = volume (created on first use).

  
Mental model
  
A mount shadows whatever the image had at that path — like mounting a USB drive over a directory. Writes to that path go to the volume/host, bypassing the writable layer entirely.

  
Named volumes survive docker rm; list with docker volume ls, delete with docker volume rm. REFERENCE


  
5.3 The two workflows you'll actually use

  
terminal

  
# 1. Persistent database (volume)
$ docker run -d -v pgdata:/var/lib/postgresql/data \
    -e POSTGRES_PASSWORD=dev postgres:16
# rm the container, run again with same -v: data still there.

# 2. Dev loop (bind mount): host code live inside the container
$ docker run -v $(pwd):/app myapp

  
Common mistakes
  
    
    
  • Bind-mounting $(pwd) over /app after the image already COPY'd code there → the mount shadows the image's copy. Fine in dev (that's the point), disaster if you do it in prod expecting image code to run.
    • 
    
  • Node.js specific: bind-mounting the project dir also shadows the image's node_modules with your host's (or with nothing). Standard fix: anonymous volume -v /app/node_modules to hole-punch it.
    • 
    
  • Forgetting the volume on a database container, then losing data on rm. Every official DB image's docs state the data path — mount it.
    • 
  


  
Exercise
  
Run Postgres with a named volume, create a table, docker rm -f the container, start a fresh one with the same volume, and confirm the table survived. Then repeat without a volume and watch the data vanish. Feeling that loss once is worth ten explanations.

06

    
Networking

    
MODE HANDS-ON

    

  


  
6.1 The model DEEP

  
Each container gets its own network namespace: its own interfaces, its own IP, its own localhost. Three consequences that explain nearly every networking bug:

  
    
    
  1. localhost inside a container is that container, not your machine, not other containers. This is the #1 networking bug.
    2. 
    
  2. An app listening on 127.0.0.1 inside a container is unreachable from outside the container — it must bind 0.0.0.0. (#2 bug — this is the exercise-1 gotcha from Part 4.)
    3. 
    
  3. Containers can't be reached from the host without explicit port publishing.
    4. 
  


  
6.2 Bridge networks and DNS DEEP

  
By default, containers attach to Docker's default bridge network — a virtual switch on the host. Containers on the same bridge can reach each other by IP.

  

    

      your machine — port publishing punches in from here
    

    

      web · nginx172.17.0.2 · :80
      db · postgres172.17.0.3 · :5432
      api · myapp172.17.0.4 · :8000
      
DNS ▶ "db" resolves automatically → postgres container

    

    
But IPs change. The real mechanism you'll use: on any user-created network, Docker runs an embedded DNS server, and container names become hostnames. That's why your Django settings will say HOST=db.

  

  
terminal

  
$ docker network create appnet
$ docker run -d --network appnet --name db postgres:16
$ docker run -d --network appnet --name api myapp
# inside api, "db" resolves → the postgres container:
#   DATABASE_HOST=db  ← this string is why your Django settings will say HOST=db

  
Gotcha
  
Name-based DNS works only on user-defined networks, not the default bridge — a classic gotcha. In practice this doesn't hurt you because Docker Compose creates a user network automatically — Part 7.


  
6.3 Port publishing DEEP

  
-p 8080:80 = "host's 8080 forwards to this container's 80" (implemented as NAT/iptables rules). Distinctions to keep straight:

  
    
    
  • Container↔container traffic on a shared network does not need -p at all — they talk directly. -p is only for reaching a container from the host/outside world.
    • 
    
  • EXPOSE in a Dockerfile publishes nothing (documentation only).
    • 
    
  • -p 8080:80 vs -p 80:80: left number is arbitrary and just has to be free on the host.
    • 
  


  
6.4 Other network drivers REFERENCE ADVANCED

  
host (no isolation — container shares host's network stack; Linux-only, niche perf cases), none (no networking), overlay (multi-host — Swarm/K8s territory). Know they exist; bridge covers everything until orchestration.


  
Exercise
  
Create a network, run two containers on it (nginx named web, and alpine with sleep 3000 named probe). docker exec into probe and wget -qO- http://web — you just used container DNS. Then try the same from a container on the default bridge and watch name resolution fail.

07

    
Docker Compose

    
MODE HANDS-ON

    

  


  
7.1 What and why DEEP

  
A real app is several containers (app + db + cache + proxy) plus networks, volumes, env vars, and startup order. Managing that with docker run commands is unmaintainable. Compose = declare the whole stack in one YAML file; one command brings it up or down. It's also the format for communicating "here's how to run this project" to other developers.

  
The key insight
  
Compose does nothing Docker can't — it's orchestration sugar over the same API. Every Compose key maps to a docker run flag you already know. That mapping is how you should read every Compose file.


  
7.2 The canonical file, annotated DEEP STRUCTURE RECOGNIZE KEYS

  
docker-compose.yml

  
# docker-compose.yml
services:                      # each service = one container definition
  web:
    build: .                   # build from local Dockerfile (vs image: for prebuilt)
    ports:
      - "8000:8000"            # = -p
    environment:               # = -e
      - DATABASE_HOST=db       # ← service name = DNS hostname (Part 6!)
    env_file: .env             # or load many from a file (keep secrets out of YAML)
    volumes:
      - .:/app                 # bind mount for live dev
    depends_on:
      db:
        condition: service_healthy   # wait for db's healthcheck, not just its start
  db:
    image: postgres:16
    environment:
      - POSTGRES_PASSWORD=${DB_PASSWORD}   # interpolated from .env
    volumes:
      - pgdata:/var/lib/postgresql/data    # named volume for persistence
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 5

volumes:
  pgdata:                      # declare named volumes here

  
Compose automatically creates a user-defined network for the project and attaches all services — which is why DATABASE_HOST=db just works with zero network config.


  
7.3 Commands RECOGNIZE

  
terminal

  
$ docker compose up -d          # build if needed, create network/volumes, start all
$ docker compose up -d --build  # force rebuild (after Dockerfile/dependency changes)
$ docker compose logs -f web
$ docker compose exec web bash
$ docker compose ps
$ docker compose down           # stop + remove containers & network (volumes SURVIVE)
$ docker compose down -v        # ...and delete volumes (⚠ deletes your database)


  
7.4 The depends_on trap DEEP — EVERYONE HITS THIS

  
Plain depends_on: [db] waits for the db container to start, not for Postgres to be ready to accept connections. Your app boots in 1s, Postgres initializes in 5s, app crashes with "connection refused."

  
Fixes, best-first: (1) healthcheck + condition: service_healthy as above; (2) retry logic in the app (what production-grade apps do anyway); (3) wait-for-it scripts (legacy).

8.2 The Dockerfile (production-shaped)

  
Dockerfile

  
FROM python:3.12-slim

# Python hygiene in containers:
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1          # unbuffered → logs appear in `docker logs` in real time

WORKDIR /app

# system deps for psycopg (libpq); clean apt lists in the SAME layer (Part 4.4)
RUN apt-get update && apt-get install -y --no-install-recommends libpq5 \
    && rm -rf /var/lib/apt/lists/*

# dependency layer first — cache optimization (Part 4.3)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# non-root user (Part 11)
RUN useradd -m appuser && chown -R appuser /app
USER appuser

EXPOSE 8000
CMD ["gunicorn", "config.wsgi:application", "--bind", "0.0.0.0:8000", "--workers", "3"]

  
Note what's applied: slim base, layer ordering, same-layer cleanup, 0.0.0.0 binding, exec-form CMD, non-root. Every line traces back to a concept from Parts 4–6.


  
8.3 docker-compose.yml

  
docker-compose.yml

  
services:
  web:
    build: .
    env_file: .env
    environment:
      - DATABASE_HOST=db        # DNS names from Part 6
      - REDIS_URL=redis://redis:6379/0

      - static:/app/staticfiles # shared with nginx

      db:

  redis:
    image: redis:7-alpine

  nginx:
    image: nginx:1.27-alpine
    ports:
      - "80:80"

      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro

volumes:
  pgdata:
  static:

server {
    listen 80;
    location /static/ { alias /staticfiles/; }

The Debugging Playbook

    
TAG DEEPMODE REFERENCE

    

  


  
Debugging Docker is systematic, not magical. The two mental models doing the work: a container is a process (Part 2) and the request path (Part 6).


  
Container exits immediately / restart loops

  
    
    
  1. docker ps -a → read the exit code. 0 = process finished normally (did you give it a long-running command?). 1/nonzero = app crashed. 137 = SIGKILL — either OOM-killed (check docker inspect → OOMKilled: true) or docker kill. 126/127 = command not executable / not found (typo in CMD, missing binary, wrong architecture).
    2. 
    
  2. docker logs <id> → the app's dying words. This solves most cases.
    3. 
    
  3. Still opaque? Override the entrypoint to get a shell in the same image and run the command by hand: docker run -it --entrypoint bash myimg.
    4. 
  


  
Can't reach the app from the browser

  
Walk the path outside-in; test each hop:

  
    
    
  1. Is the container running and is the port published? (docker ps shows 0.0.0.0:8080->80.)
    2. 
    
  2. Is the app listening on 0.0.0.0, not 127.0.0.1? (docker exec in, check with ss -tlnp or the app's config — this is the answer 4 times out of 5.)
    3. 
    
  3. Right port? Published container-port must match what the app actually binds.
    4. 
    
  4. From inside the container itself, does curl localhost:8000 work? If yes, the app is fine and the problem is wiring; if no, it's the app.
    5. 
  


  
Container A can't reach container B

  
    
    
  1. Same network? docker network inspect <net> lists members.
    2. 
    
  2. Using the service/container name as hostname, not localhost? (localhost bug again.)
    3. 
    
  3. B actually up and healthy? Race condition? (Part 7.4.)
    4. 
    
  4. Test resolution from inside A: docker exec -it A sh → ping b / nc -zv b 5432.
    5. 
  


  
Build fails / behaves stale

  
    
    
  • Read which STEP failed — the error is about that instruction's layer.
    • 
    
  • "Works on rebuild but changes don't appear" → stale cache or you edited a file excluded by .dockerignore; docker compose up --build or docker build --no-cache to prove/disprove.
    • 
    
  • File-not-found during COPY → path is relative to build context, and check .dockerignore.
    • 
  


  
Disk full REFERENCE

  
docker system df to see usage; docker system prune (add -a to also drop unused images; add --volumes only if you mean it).


  
The debugging habit
  
Before Googling, always run these three: docker ps -a (state + exit code), docker logs (why), docker inspect (config reality vs your assumption). Most "Docker bugs" are one of five things: localhost confusion, 127.0.0.1 binding, missing volume, race with the DB, stale cache. You now know all five.

Internals: What's Actually Happening

    
TAG ADVANCED★ INTERVIEW GOLD

    

  


  
When to return
  
Return here after Part 8. This section upgrades Part 2's mental model to the mechanism level. Nothing here is needed to use Docker; all of it is what separates "I use Docker" from "I understand Docker" in a senior interview.


  
10.1 Namespaces — the isolation mechanism

  
A namespace is a kernel feature that gives a process a private view of one global resource. Docker uses six:

  

    
NamespaceIsolatesEffect in a container

    
      
PIDProcess treeContainer's process is PID 1; can't see host processes

      
NETNetwork stackOwn interfaces, own IP, own ports, own localhost

      
MNTMount tableOwn filesystem root

      
UTSHostnamehostname shows container ID

      
IPCShared memoryCan't talk to host processes via IPC

      
USERUID mappingroot inside can map to non-root outside ADVANCED

    
  

  
Proof it's "just a process": on a Linux host, docker inspect -f '{{.State.Pid}}' c gives a host PID; ls /proc/<pid>/ns/ shows its namespace handles. docker exec literally means "start a process and join these namespaces" (the setns syscall).


  
10.2 Cgroups — the resource mechanism

  
Namespaces control visibility; cgroups control consumption. --memory=512m --cpus=1.5 writes limits into the cgroup filesystem (/sys/fs/cgroup/...), and the kernel enforces them. Exceed the memory limit → kernel OOM-killer terminates the process → exit code 137. That's the whole story behind Part 9's 137.


  
10.3 OverlayFS — the image mechanism

  
The union filesystem implementing Part 2's layer diagram. Mechanics worth knowing:

  
    
    
  • lowerdir = image layers (read-only, stacked), upperdir = container's writable layer, presented merged.
    • 
    
  • Reads fall through the stack top-down until a layer has the file.
    • 
    
  • Copy-on-write: modifying a file from a lower layer first copies the whole file up to upperdir, then edits it. (Hence: containers writing heavily to big files should use volumes — volumes bypass overlay entirely, which is also why DB data lives on volumes for performance, not just persistence.)
    • 
    
  • Deleting a lower-layer file creates a "whiteout" marker in upperdir — the file is hidden, not removed. This is the mechanical reason deleting files in a later Dockerfile layer doesn't shrink the image (Part 4.4).
    • 
  


  
10.4 The runtime stack: dockerd → containerd → runc

  
    
    
  • dockerd: API server + the high-level features (builds, networks, volumes).
    • 
    
  • containerd: container lifecycle supervisor (also used directly by Kubernetes — this is why "Kubernetes dropped Docker" headlines didn't mean what people thought: K8s dropped dockerd as a middleman and talks to containerd directly; your Docker-built images run unchanged).
    • 
    
  • runc: small CLI that makes the actual syscalls — clone() with namespace flags, cgroup writes, pivot_root into the overlay mount, then exec() your CMD. Then it exits; a tiny shim keeps the container's stdio alive. runc implements the OCI runtime spec, and images follow the OCI image spec — which is why images are portable across Docker/Podman/Kubernetes/cloud runtimes.
    • 
  


  
10.5 docker run, the full internal answer

  
interview-brain.txt

  
CLI → REST API → dockerd resolves image (pull layers if missing, verify
digests) → containerd creates container metadata → prepares overlay mount
(image layers as lowerdirs + fresh upperdir) → allocates network namespace,
veth pair into the bridge, IP from the bridge subnet, iptables NAT rules
for -p → runc clones a process with new namespaces, applies cgroups,
pivots root into the merged filesystem, drops capabilities, execs the CMD
→ shim holds stdio/exit code → dockerd streams logs from the process's
stdout. When PID 1 exits, the container is "exited" with that code.

  
Senior bar
  
If you can deliver that paragraph unprompted and unpack any step on request, you're past most interview bars.

Production & Security

    

    

  


  
The subset that's actually expected of a developer (ops teams own the rest):

  
    
    
  1. Don't run as root DEEP. Default is root-in-container; a container escape then means root-adjacent on the host (shared kernel!). The USER appuser lines in Part 8 are the fix. This is the single most-asked Docker security question.
    2. 
    
  2. Never bake secrets into images DEEP. No passwords in Dockerfile ENV/COPY — layers are readable by anyone with the image (docker history shows all). Inject at runtime: env vars/env_file at minimum; secret managers in real prod.
    3. 
    
  3. Pin versions DEEP CONCEPT. FROM python:3.12-slim, postgres:16 — never latest in anything that redeploys. Tags move (Part 4.5); unpinned = unreproducible.
    4. 
    
  4. Resource limits RECOGNIZE: --memory/--cpus (or compose deploy.resources) so one leaking container can't starve the host.
    5. 
    
  5. Healthchecks + restart policy RECOGNIZE: HEALTHCHECK / compose healthcheck + restart: unless-stopped = self-healing at the single-host level.
    6. 
    
  6. Log to stdout, stay stateless DEEP AS DESIGN PRINCIPLE: containers should be disposable — all state in volumes/external services, all logs on stdout. This is what makes horizontal scaling and orchestration possible, and it's the philosophical core of "cloud-native."
    7. 
    
  7. Image scanning (docker scout, trivy), read-only root fs, dropped capabilities — REFERENCE/ADVANCED: know the terms.
    8.

When Docker Is and Isn't the Right Tool

    
TAG DEEP

    

  


  
Genuinely strong candidates can argue against the tool.

  

    

      
USE IT WHEN

      
    
        
  • Multi-service dev environments (the Part 8 stack — its best everyday use)
    • 
        
  • Parity between dev/CI/prod
    • 
        
  • Deploying to any container platform
    • 
        
  • Running two conflicting stacks on one machine
    • 
        
  • Onboarding ("clone, docker compose up, done")
    • 
        
  • Shipping software to strangers' machines
    • 
      

    

    

      
SKIP OR QUESTION IT WHEN

      
    
        
  • Simple scripts/single static binaries — a Go binary or a cron script may need nothing
    • 
        
  • GUI/desktop apps — wrong tool
    • 
        
  • Extreme performance/hardware coupling (HFT, GPU quirks, kernel modules) — the abstraction costs you
    • 
        
  • Hard multi-tenant security isolation — shared kernel; hostile workloads want VMs (or gVisor/Firecracker — recognize the names)
    • 
        
  • Windows/macOS native targets — Linux containers only run natively on Linux; Docker Desktop runs a hidden Linux VM (worth knowing: this is why file-heavy bind mounts are slow on Mac)
    • 
        
  • A solo dev on a tiny app with no deployment story — Docker adds a layer of indirection you must debug; adopt it when the pain it removes exceeds the pain it adds
    • 
      

    

  

  
Also honest to know: Compose is single-host. Multi-host scheduling, autoscaling, rolling deploys = orchestrators (Kubernetes). Docker is the packaging + runtime; K8s is fleet management of the same containers.
