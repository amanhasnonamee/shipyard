01
Where SQL Came From
TAG DEEP

You cannot understand why SQL looks nothing like other programming languages until you know what it was designed to replace.

The problem before relational databases

In the 1960s, data was stored in hierarchical and network databases (IBM's IMS, CODASYL systems). To retrieve anything, a programmer wrote code that *navigated pointers* — follow this record to that one, walk this chain. Three consequences:

  1. Every query was a program. Answering a new question meant writing and compiling new navigation code.
  1. The physical layout leaked into every program. Reorganize the storage, and every program broke.
  1. Only specialists could ask questions. There was no way for an analyst to interrogate the data.

The lineage

The three ideas actually invented here

  1. Declarative querying. You describe the result you want; the system's query optimizer decides how to get it — which indexes to use, which join algorithm, in what order. No other mainstream language works this way. It's why SQL can get faster when you upgrade your database without changing a line of your code, and why "how do I make this faster?" is usually answered by helping the optimizer rather than by rewriting logic.
  1. Physical/logical separation (data independence). Your query names tables and columns, never files, offsets, or pointers. Storage can be reorganized, indexed, partitioned, or replicated underneath you and your query still works. This was the entire point of Codd's paper.
  1. Set-based thinking. Operations apply to whole sets of rows at once, not one row at a time. This is the mental shift that separates people who write SQL from people who write loops in SQL's clothing — and it's the single biggest determinant of query performance.

The framing worth being able to say

*"SQL is a declarative language over a mathematical model of data. You state the shape of the answer as a set operation, and the optimizer chooses the execution strategy. Almost everything that feels odd about SQL — the clause order, three-valued logic with NULL, the fact that it isn't procedural — follows from those two facts: it describes relations, and it doesn't describe execution."*

02
The Core Mental Model
TAG DEEP

Five ideas. This is the most important section in the document; everything else is detail built on top of it.

Idea 1: A table is a set of rows, and SQL operates on whole sets

A table is an unordered collection of rows, each with the same named, typed columns. Two consequences that beginners find surprising and that matter enormously:

  • There is no inherent order. Rows do not have positions. Without ORDER BY, the order you get is whatever the engine found convenient, and it can change between runs, after an update, or after a version upgrade. If order matters, say so explicitly — every time.
  • There is no "current row." Unlike a spreadsheet or a for loop, SQL has no cursor walking down the data. A WHERE clause is not "check each row"; it is "define the subset of rows for which this is true." The engine may check them in any order, in parallel, or skip most of them entirely using an index.

The practical discipline: think in sets, not loops. "For each customer, find their latest order" is a loop-shaped thought that produces slow, awkward SQL. "Join customers to their orders, then keep only the ones ranked first per customer" is set-shaped and fast. Training yourself to reframe is most of learning SQL well.

terminal
Loop thinking (slow, procedural, often wrong):
  for each row in customers:
      run a query to get that customer's orders

Set thinking (one query, one plan, one pass):
  join the two sets, then filter the combined set

Idea 2: Every query is a pipeline of set transformations, evaluated in a fixed logical order

This is the single most clarifying fact in all of SQL. You write clauses in one order, but the database logically evaluates them in a different one:

terminal
Written order:            Logical evaluation order:
SELECT    ...             1. FROM      — get the source tables
FROM      ...             2. JOIN      — combine them into one big set
JOIN      ...             3. WHERE     — filter individual rows
WHERE     ...             4. GROUP BY  — collapse rows into groups
GROUP BY  ...             5. HAVING    — filter the groups
HAVING    ...             6. SELECT    — compute the output columns
ORDER BY  ...             7. DISTINCT  — remove duplicate output rows
LIMIT     ...             8. ORDER BY  — sort the result
                          9. LIMIT     — take the first N

Nearly every "why doesn't this work?" question in SQL is answered by this list:

  • Why can't I use a column alias defined in SELECT inside my WHERE? Because WHERE (step 3) runs before SELECT (step 6). The alias doesn't exist yet. You *can* use it in ORDER BY (step 8), which runs after.
  • **Why does WHERE reject aggregate functions like COUNT(*)?** Because WHERE runs before GROUP BY. There are no groups yet, so there's nothing to count. That's exactly why HAVING exists — it's a filter that runs *after* grouping.
  • Why is WHERE faster than HAVING for the same condition? WHERE throws rows away before the expensive grouping work; HAVING does the grouping first and then discards. Filter as early as possible.
  • Why did LIMIT 10 give me different rows this time? Because without ORDER BY, step 9 takes ten arbitrary rows from an unordered set (Idea 1).

Memorize this pipeline. It converts SQL from a pile of rules into a machine you can reason about.

Idea 3: NULL is not a value — it's the absence of one, and it makes logic three-valued

NULL means "unknown" or "not applicable." It is not zero, not an empty string, not false. And this changes logic itself: every comparison yields TRUE, FALSE, or UNKNOWN.

sql
NULL = NULL        -- UNKNOWN, not TRUE!  (is one unknown thing equal to another? unknowable)
NULL = 5           -- UNKNOWN
NULL <> 5          -- UNKNOWN
5 + NULL           -- NULL  (any arithmetic with unknown is unknown)
'abc' || NULL      -- NULL  (in most databases; string concatenation too)

The rule that makes this practical: WHERE keeps only rows where the condition is TRUE. UNKNOWN is discarded exactly like FALSE. So:

sql
SELECT * FROM users WHERE country = 'IN';       -- rows with NULL country are excluded
SELECT * FROM users WHERE country <> 'IN';      -- rows with NULL country are ALSO excluded!

Both queries exclude NULL rows, so the two results together do not add up to the whole table. This surprises everyone once, and it silently corrupts reports.

Testing for NULL requires special syntax, because = NULL never matches:

sql
WHERE country IS NULL          -- correct
WHERE country IS NOT NULL      -- correct
WHERE country = NULL           -- always UNKNOWN → never matches. A silent bug

Other NULL behaviours you must know [DEEP]:

SituationBehaviour
COUNT(*)Counts rows, including those with NULLs
COUNT(column)Counts non-NULL values only — the difference is a classic interview question
SUM, AVG, MAXIgnore NULLs. AVG divides by the count of non-NULL values, which can quietly differ from what you meant
GROUP BYTreats all NULLs as one group (inconsistent with = semantics, but that's the standard)
ORDER BYNULLs sort together, first or last depending on the database; NULLS FIRST/NULLS LAST controls it explicitly
UNIQUE constraintUsually permits multiple NULLs, because two NULLs aren't "equal"
IN (1, 2, NULL)Fine. But NOT IN (1, 2, NULL) never returns any rows — a notorious trap explained in Part 6

Useful tools: COALESCE(a, b, c) returns the first non-NULL argument; NULLIF(a, b) returns NULL when the two are equal (handy for avoiding division by zero).

Idea 4: A join is a set operation that produces a new, wider set of rows

A join does not "add columns to a table." Conceptually, it forms combinations of rows from two tables and keeps the ones satisfying your condition. The output is a *new* set whose rows are wider — and whose row *count* may be larger or smaller than either input.

That last point is where most join bugs live. If one order has three line items, joining orders to line items yields three rows for that order, and any SUM over an order-level column now triple-counts. Understanding that a join *multiplies* rows when the relationship is one-to-many is the difference between correct and confidently wrong reports. Part 4 covers this in full.

Idea 5: The optimizer decides how; you only decide what

When you submit a query, the database:

  1. Parses it into a syntax tree.
  1. Rewrites it into a canonical logical form (flattening subqueries, pushing filters down).
  1. Plans it: enumerates possible execution strategies — which index to use, which join algorithm (nested loop, hash, merge), what order to join tables in — and estimates the cost of each using statistics about your data (row counts, value distributions).
  1. Executes the cheapest plan it found.

Three consequences that shape all of Parts 9–11:

  • Two differently-written queries that mean the same thing often produce the identical plan — so "clever" rewriting is usually pointless. The optimizer already did it.
  • When a query is slow, the fix is almost never "write it differently." It's giving the optimizer better options (an index), better information (fresh statistics), or less work (filter earlier, return fewer rows).
  • The plan is *estimated*, so it can be wrong. Stale statistics or unusual data distributions produce bad plans, which is why EXPLAIN ANALYZE (Part 9) compares estimates against reality.

Checkpoint — do this before Part 3

Answer these out loud or in writing, without looking:

  1. Why can't you reference a SELECT alias in the WHERE clause, but you can in ORDER BY?
  1. A table has 100 rows; 20 have NULL in city. WHERE city = 'Delhi' returns 30 rows and WHERE city <> 'Delhi' returns 50. Where did the other 20 go, and why is that correct?
  1. What's the difference between COUNT(*) and COUNT(city) on that table?
  1. You run the same query twice with no data changes and get rows in a different order. Is the database broken? Why or why not?
  1. Why is filtering in WHERE generally cheaper than the same filter in HAVING?

If any of these is shaky, reread Part 2. Nothing later will stick without it.

Querying One Table

Now hands-on. Create a database and follow along; reading SQL teaches you almost nothing.

3.1 SELECT — projecting columns [DEEP concept, RECOGNIZE syntax]

sql
SELECT id, name, city FROM customers;         -- name the columns you want
SELECT * FROM customers;                       -- all columns

SELECT * is fine when exploring interactively and a bad habit in saved code: it returns more data than you need (slower over the network), silently changes shape when someone adds a column, and hides which columns your code actually depends on. Name your columns in anything you keep.

Expressions and aliases:

sql
SELECT
  name,
  price * quantity           AS line_total,      -- computed column
  UPPER(city)                AS city_upper,
  price * 0.18               AS tax
FROM order_items;

AS names the output column. Quoting rules differ by dialect; using lowercase names with underscores avoids the entire problem.

3.2 WHERE — filtering rows [DEEP]

sql
SELECT * FROM orders
WHERE status = 'shipped'                        -- equality
  AND total > 500                               -- comparison
  AND created_at >= '2026-01-01'                -- dates compare naturally
  AND region IN ('north', 'east')               -- set membership
  AND total BETWEEN 100 AND 999                 -- inclusive on both ends
  AND customer_name LIKE 'A%'                   -- pattern: % = any chars, _ = one char
  AND notes IS NOT NULL;                        -- NULL test (Idea 3)

Points that matter more than the syntax:

  • Operator precedence: AND binds tighter than OR. WHERE a AND b OR c means (a AND b) OR c. Always parenthesize mixed conditions — this is a real source of wrong-but-plausible results.
  • LIKE 'A%' can use an index; LIKE '%A' cannot. A leading wildcard forces the engine to examine every row, because indexes are ordered by the start of the value (Part 10 explains why). For real text search, use full-text search features rather than LIKE '%term%'.
  • Case sensitivity varies: Postgres is case-sensitive by default, MySQL usually isn't. Use LOWER() on both sides or a case-insensitive collation when you need certainty.
  • Wrapping a column in a function usually disables its index. WHERE YEAR(created_at) = 2026 typically cannot use an index on created_at, while WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01' can. This single rewrite is one of the most common real-world speedups.

3.3 ORDER BY, LIMIT, DISTINCT [RECOGNIZE]

sql
SELECT DISTINCT city FROM customers ORDER BY city;

SELECT * FROM orders
ORDER BY created_at DESC, id ASC        -- tiebreaker makes results deterministic
LIMIT 20 OFFSET 40;                     -- page 3 of 20-row pages

Two notes: ORDER BY with no tiebreaker on a non-unique column gives unstable results across runs — always add a unique column as the final sort key. And OFFSET gets progressively slower as it grows, because the engine must generate and discard all the skipped rows; Part 11 covers keyset pagination as the fix.

3.4 Data types [DEEP enough to avoid disasters]

CategoryTypesWhat to know
IntegersINTEGER, BIGINT, SMALLINTUse BIGINT for IDs on anything that might grow; running out of 32-bit IDs in production is a real and painful event
Exact decimalsNUMERIC(12,2) / DECIMALAlways use this for money. Exact base-10 arithmetic
FloatsREAL, DOUBLE PRECISIONBinary approximations. 0.1 + 0.2 <> 0.3. Correct for measurements and scientific data, never for money
TextTEXT, VARCHAR(n), CHAR(n)In Postgres these perform identically; VARCHAR(n) just adds a length check. CHAR(n) pads with spaces and causes surprises — avoid
Dates & timesDATE, TIMESTAMP, TIMESTAMPTZ, INTERVALStore timestamps in UTC (TIMESTAMPTZ in Postgres) and convert at display time. Timezone bugs are among the most expensive and hardest to notice

The rule underneath the table: types are constraints, and constraints are documentation the database enforces. Storing a date as text or money as float works right up until it silently doesn't.

3.5 Exercises

  1. Create a customers table and an orders table, insert ~20 rows by hand, and deliberately leave some values NULL.
  1. Write a query that proves Idea 3: show that WHERE col = 'x' and WHERE col <> 'x' don't sum to the table's row count, then fix it with IS NULL.
  1. Write a query with mixed AND/OR without parentheses, predict the result, then add parentheses to change it — and confirm your prediction was right.
  1. Find the 5 most recent orders with a deterministic tiebreaker.

Joins: Combining Tables

Joins are where SQL becomes powerful and where most mistakes happen. Take this part slowly.

4.1 Why joins exist [DEEP]

Relational design deliberately splits data across tables so each fact is stored exactly once (Part 7 covers why — normalization). A customer's name lives in customers; their orders live in orders, referencing the customer by customer_id. That reference is a foreign key.

The cost of splitting is that answering real questions requires recombining. That recombination is a join. So: normalization is the reason joins exist, and joins are the price of not duplicating data. Understanding that trade-off is the heart of relational thinking.

4.2 The join types [DEEP]

sql
SELECT c.name, o.id, o.total
FROM customers c
JOIN orders o ON o.customer_id = c.id;
JoinKeepsUse when
INNER JOIN (or just JOIN)Only rows with a match in both tablesThe default. "Customers who have orders"
LEFT JOIN (LEFT OUTER JOIN)All left rows; NULLs where the right has no match"All customers, with their orders if any" — including customers with none
RIGHT JOINAll right rowsRare; flip the table order and use LEFT for readability
FULL OUTER JOINAll rows from both sidesReconciling two datasets to find what's missing on each side
CROSS JOINEvery combination (Cartesian product)Deliberately generating combinations — e.g. every product × every region for a report grid

A picture of what LEFT JOIN does:

terminal
customers          orders                  LEFT JOIN result
id name            customer_id total        name    total
1  Asha            1            500         Asha    500
2  Bilal           1            300         Asha    300
3  Chen            3            900         Bilal   NULL   ← kept, padded with NULLs
                                            Chen    900

4.3 The three join mistakes everyone makes [DEEP — read twice]

Mistake 1: unintentional row multiplication.

sql
-- orders has 1 row per order; order_items has N rows per order
SELECT o.id, SUM(o.total)          -- WRONG: o.total is counted once per item
FROM orders o
JOIN order_items i ON i.order_id = o.id
GROUP BY o.id;

If an order has 3 items, o.total appears 3 times and the sum is tripled. This produces numbers that look reasonable and are wrong — the most dangerous kind of bug. The fix is to aggregate at the correct grain, usually by aggregating the many-side in a subquery or CTE first (Part 6), or by summing the item-level column instead.

Diagnostic habit: whenever you add a join, check whether your row count changed unexpectedly. SELECT COUNT(*) before and after is a two-second sanity check that catches this class of error permanently.

Mistake 2: filtering a LEFT JOIN in WHERE, which silently turns it into an INNER JOIN.

sql
-- Intent: all customers, plus their 2026 orders
SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.created_at >= '2026-01-01';       -- BUG: drops customers with no orders

The LEFT JOIN dutifully produced NULL rows for order-less customers — and then WHERE evaluated NULL >= '2026-01-01' as UNKNOWN and discarded them (Idea 3 again). The fix is to move the condition into the ON clause, which filters *during* the join rather than after:

sql
LEFT JOIN orders o
  ON o.customer_id = c.id
 AND o.created_at >= '2026-01-01';        -- correct: still keeps all customers

The rule to carry: conditions on the outer (preserved) table belong in WHERE; conditions on the optional table belong in ON.

Mistake 3: forgetting the join condition entirely, producing a CROSS JOIN. 10,000 rows joined to 10,000 rows is 100,000,000 rows. The symptom is a query that never finishes or fills the disk. Always check that every joined table has a condition connecting it to the rest.

4.4 Self-joins and multi-table joins [RECOGNIZE]

A table can join to itself — the standard way to relate rows within one table (employees to their managers, comparing a row to the previous one):

sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;   -- LEFT so the CEO isn't dropped

Multi-table joins chain the same way; alias every table and qualify every column (o.id, not bare id) so ambiguity is impossible and the query stays readable when someone adds a column later.

4.5 Set operations [RECOGNIZE]

These combine the *results* of queries vertically, rather than joining horizontally:

sql
SELECT city FROM customers
UNION            -- combines and REMOVES duplicates (costs a sort/hash)
SELECT city FROM suppliers;

SELECT city FROM customers
UNION ALL        -- combines and KEEPS duplicates — faster; prefer when you don't need dedup
SELECT city FROM suppliers;

INTERSECT (in both) and EXCEPT/MINUS (in the first but not the second) round out the set algebra — EXCEPT is an elegant way to answer "what's missing?" and a great tool for reconciling two sources.

4.6 Exercises

  1. Build the multiplication bug deliberately: create an order with 3 items, SUM the order total across a join, and observe the tripling. Then fix it two different ways.
  1. Write the "all customers plus their 2026 orders" query wrongly (in WHERE), see customers disappear, then fix it in ON.
  1. Write a self-join listing every employee with their manager's name, ensuring the top-level employee still appears.
  1. Use EXCEPT to find customers who have never placed an order, then write the same thing with a LEFT JOIN ... WHERE o.id IS NULL. Compare.

05
Aggregation and Grouping

5.1 Aggregate functions [DEEP concept]

An aggregate collapses many rows into one value:

sql
SELECT
  COUNT(*)            AS orders,          -- rows
  COUNT(discount_code) AS with_code,      -- non-NULL values only (Idea 3)
  COUNT(DISTINCT customer_id) AS buyers,
  SUM(total)          AS revenue,
  AVG(total)          AS avg_order,
  MIN(created_at)     AS first_order,
  MAX(total)          AS biggest
FROM orders;

With no GROUP BY, the whole table is one group, so you get exactly one row.

5.2 GROUP BY [DEEP]

sql
SELECT city, COUNT(*) AS orders, SUM(total) AS revenue
FROM orders
GROUP BY city;

The mental model: GROUP BY partitions the rows into buckets by the listed columns; each aggregate then runs once per bucket, and you get one output row per bucket.

The rule that causes the most errors: every column in SELECT must either appear in GROUP BY or be inside an aggregate function. Reason: if you group by city, there are many customer_name values in each bucket and the database has no basis to choose one. Postgres and SQL Server raise an error; MySQL historically returned an arbitrary value, which is worse because it hides the mistake.

5.3 HAVING vs WHERE [DEEP]

sql
SELECT city, SUM(total) AS revenue
FROM orders
WHERE created_at >= '2026-01-01'    -- filters ROWS, before grouping
GROUP BY city
HAVING SUM(total) > 10000           -- filters GROUPS, after aggregation
ORDER BY revenue DESC;

Straight from Idea 2's pipeline: WHERE runs at step 3, HAVING at step 5. So WHERE cannot see aggregates and HAVING can. And putting a row-level condition in HAVING still works but is slower, because you grouped rows you were going to throw away.

5.4 Beyond basic grouping [RECOGNIZE]

FILTER (Postgres) or CASE inside aggregates lets you compute several conditional metrics in one pass — vastly better than running three separate queries:

sql
SELECT
  city,
  COUNT(*)                                        AS all_orders,
  COUNT(*) FILTER (WHERE status = 'cancelled')    AS cancelled,
  SUM(total) FILTER (WHERE status = 'shipped')    AS shipped_revenue,
  -- portable equivalent using CASE:
  SUM(CASE WHEN status = 'refunded' THEN 1 ELSE 0 END) AS refunded
FROM orders
GROUP BY city;

GROUPING SETS, ROLLUP, and CUBE produce subtotals and grand totals in one query — useful for reporting. [REFERENCE]

5.5 Common mistakes

  • Averaging an average. AVG of per-city averages is not the overall average unless every city has the same row count. Aggregate from the base rows.
  • AVG silently skipping NULLs and changing the denominator — if NULL should count as zero, use AVG(COALESCE(col, 0)) deliberately.
  • Counting after a one-to-many join and getting inflated numbers (Part 4.3) — use COUNT(DISTINCT ...) or fix the grain.
  • Using HAVING where WHERE belongs.

5.6 Exercises

  1. Produce revenue by city and month, sorted descending, for a specific year — using WHERE for the year and HAVING for a revenue floor.
  1. Write one query returning total, cancelled, and shipped counts per city using conditional aggregation, then verify it against three separate queries.
  1. Demonstrate that averaging averages gives the wrong answer, with real numbers.

06
Subqueries, CTEs, and Window Functions

This part is where intermediate SQL becomes advanced SQL. Window functions in particular replace whole categories of painful workarounds.

6.1 Subqueries [RECOGNIZE the forms, DEEP on correlated ones]

A query nested inside another. Three positions:

sql
-- 1. Scalar subquery (returns one value)
SELECT name, (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.id) AS order_count
FROM customers c;

-- 2. In WHERE, as a set
SELECT * FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE total > 1000);

-- 3. As a derived table in FROM
SELECT city, AVG(order_count) FROM (
  SELECT customer_id, city, COUNT(*) AS order_count
  FROM orders GROUP BY customer_id, city
) per_customer
GROUP BY city;

Correlated subqueries (form 1 above) reference the outer query's row, so conceptually they run once per outer row. Modern optimizers often rewrite them into joins — but not always, and when they don't, this is a genuine performance cliff on large tables. Prefer a join or a CTE when the row count is large.

EXISTS vs IN vs NOT IN [DEEP]:

sql
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id)   -- stops at first match
WHERE id IN (SELECT customer_id FROM orders)                        -- builds the full set
WHERE id NOT IN (SELECT customer_id FROM orders)                    -- ⚠ DANGER

The NOT IN trap, and it's a serious one: if the subquery returns even one NULL, NOT IN returns no rows at all. Why? x NOT IN (1, NULL) expands to x <> 1 AND x <> NULL, and the second half is always UNKNOWN, so the whole condition can never be TRUE (Idea 3). Use NOT EXISTS instead — it is NULL-safe and usually faster. This is one of the highest-value facts in this entire document, because the failure is silent.

6.2 Common Table Expressions (CTEs) [DEEP — the readability tool]

sql
WITH monthly AS (
  SELECT date_trunc('month', created_at) AS month, city, SUM(total) AS revenue
  FROM orders
  GROUP BY 1, 2
),
ranked AS (
  SELECT *, RANK() OVER (PARTITION BY month ORDER BY revenue DESC) AS rk
  FROM monthly
)
SELECT month, city, revenue
FROM ranked
WHERE rk <= 3
ORDER BY month, rk;

A CTE names an intermediate result so you can build a query in readable steps and reference each step by name. This is the single biggest improvement you can make to complex SQL: instead of five levels of nested subqueries read inside-out, you get a top-to-bottom pipeline that reads like the pipeline in Idea 2.

Notes: CTEs can reference earlier CTEs (not later ones); in Postgres 12+ they're inlined and optimized like subqueries (older versions materialized them, which was sometimes a performance trap); and recursive CTEs (WITH RECURSIVE) traverse hierarchies and graphs — org charts, category trees, dependency chains, shortest paths. [ADVANCED but genuinely worth learning once]

6.3 Window functions [DEEP — the most valuable advanced topic in SQL]

A window function computes a value across a set of related rows without collapsing them. That's the whole idea, and it's what makes it different from GROUP BY:

terminal
GROUP BY:        10 rows in → 3 rows out (rows are collapsed)
Window function: 10 rows in → 10 rows out (each row gains a computed column)
sql
SELECT
  id, customer_id, created_at, total,

  -- ranking within each customer's orders
  ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) AS recency,

  -- aggregates that don't collapse rows
  SUM(total)   OVER (PARTITION BY customer_id) AS customer_lifetime_value,
  AVG(total)   OVER (PARTITION BY customer_id) AS customer_avg,

  -- running total, ordered
  SUM(total)   OVER (ORDER BY created_at
                     ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,

  -- reach into neighbouring rows
  LAG(total)   OVER (PARTITION BY customer_id ORDER BY created_at) AS prev_order_total,
  LEAD(total)  OVER (PARTITION BY customer_id ORDER BY created_at) AS next_order_total
FROM orders;

Anatomy of the OVER clause:

  • PARTITION BY — split rows into groups (like GROUP BY, but without collapsing).
  • ORDER BY — order rows within each partition; required for anything positional (ROW_NUMBER, LAG, running totals).
  • Frame (ROWS BETWEEN ...) — which rows around the current one to include. Defaults are subtle: with ORDER BY present, the default frame includes everything from the start of the partition through the current row's peers, which is what makes running totals work.

The function families worth knowing [RECOGNIZE]:

FamilyFunctionsUse
RankingROW_NUMBER, RANK, DENSE_RANK, NTILE"Top N per group", deduplication, percentile buckets
OffsetLAG, LEAD, FIRST_VALUE, LAST_VALUEPeriod-over-period change, gaps between events
Aggregate-as-windowSUM, AVG, COUNT, MIN, MAX with OVERRunning totals, moving averages, share-of-total

ROW_NUMBER vs RANK vs DENSE_RANK on ties — a guaranteed interview question: for values 10, 10, 9, ROW_NUMBER gives 1, 2, 3 (arbitrary tiebreak); RANK gives 1, 1, 3 (gap); DENSE_RANK gives 1, 1, 2 (no gap).

The canonical pattern — "the latest row per group," which appears in every real codebase:

sql
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC) AS rn
  FROM orders
)
SELECT * FROM ranked WHERE rn = 1;

Note *why* the CTE is necessary: window functions are computed at step 6 of the pipeline (with SELECT), so WHERE (step 3) cannot reference them. You must wrap and filter outside. That's Idea 2 paying off again.

Designing Schemas: DDL, Constraints, Normalization

Querying well matters less than designing well: a good schema makes correct queries easy and incorrect ones impossible.

7.1 Creating tables [RECOGNIZE syntax, DEEP on constraints]

sql
CREATE TABLE customers (
  id          BIGSERIAL PRIMARY KEY,               -- auto-incrementing surrogate key
  email       TEXT        NOT NULL UNIQUE,
  name        TEXT        NOT NULL,
  city        TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id           BIGSERIAL PRIMARY KEY,
  customer_id  BIGINT      NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
  status       TEXT        NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending','shipped','cancelled','refunded')),
  total        NUMERIC(12,2) NOT NULL CHECK (total >= 0),
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

7.2 Constraints are the database defending your data [DEEP]

ConstraintGuaranteesWhy it matters
PRIMARY KEYUnique + not null; the row's identityEvery table should have one. It's also how other tables reference this one
FOREIGN KEY (REFERENCES)The referenced row existsPrevents orphaned records — the most common form of data corruption
NOT NULLA value is always presentRemoves a whole class of NULL-handling bugs downstream
UNIQUENo duplicatesEnforces business identity (one account per email)
CHECKAn arbitrary rule holdsEncodes domain rules (total >= 0, valid status values) where they can't be bypassed
DEFAULTA sensible value when unspecifiedFewer NULLs, less client-side logic

The principle: application code is one of many paths to your data — there will also be scripts, migrations, admin tools, another service, and someone in a SQL console at 2am. Only the database can enforce a rule against all of them. Constraints are not bureaucracy; they're the last line of defence, and they're documentation that cannot go out of date.

On ON DELETE behaviour: RESTRICT/NO ACTION blocks deleting a parent with children (usually what you want), CASCADE deletes children too (convenient and dangerous — easy to delete far more than intended), SET NULL orphans them deliberately.

7.3 Keys [DEEP]

  • A natural key is real-world data that identifies a row (email, ISBN). A surrogate key is a meaningless generated identifier (auto-increment integer, UUID).
  • Prefer surrogate primary keys: real-world identifiers change (people change email addresses), and a changing primary key means updating every referencing row.
  • Still enforce natural uniqueness with a UNIQUE constraint — you want both.
  • Auto-increment integers are compact, index-friendly, and ordered; UUIDs are globally unique and don't leak counts or require a central sequence, at the cost of size and (for random UUIDs) worse index locality. Both are defensible; know the trade-off.

7.4 Normalization [DEEP — the core of relational design]

Normalization means organizing data so each fact is stored exactly once. The forms, in plain language:

  • 1NF: each column holds a single atomic value; no comma-separated lists stuffed in a text field, no repeating column groups like phone1, phone2, phone3.
  • 2NF: no column depends on only part of a composite key.
  • 3NF: no column depends on another non-key column. If city determines state, storing both on every order means one city could end up mapped to two states.

In practice, "3NF" reduces to a habit: if you find yourself updating the same fact in more than one place, the schema is wrong.

Why it matters: duplicate storage means the copies will eventually disagree, and then there's no answer to "which one is true?" Normalization makes disagreement structurally impossible.

Denormalization is the deliberate reintroduction of duplication for read performance — storing an order's total instead of recomputing from line items, or keeping a comment_count on a post. It's legitimate when you measure a real problem and accept the maintenance burden of keeping copies in sync. Do it knowingly, never accidentally, and never before you've measured.

7.5 Modifying schemas and data [RECOGNIZE]

sql
ALTER TABLE orders ADD COLUMN notes TEXT;
ALTER TABLE orders ALTER COLUMN status SET DEFAULT 'pending';
CREATE INDEX idx_orders_customer ON orders(customer_id);

INSERT INTO customers (email, name) VALUES ('a@example.com', 'Asha')
  ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name;   -- upsert (Postgres)

UPDATE orders SET status = 'shipped' WHERE id = 42;
DELETE FROM orders WHERE created_at < '2020-01-01';

The habit that prevents catastrophe: before running any UPDATE or DELETE, run it as a SELECT with the same WHERE clause and confirm the row count is what you expect. A missing WHERE on an UPDATE rewrites the entire table, and there is no undo outside a transaction. Which is why Part 11's first rule is: wrap destructive changes in an explicit transaction so you can ROLLBACK.

Debugging and Reading Query Plans
TAG DEEP

SQL debugging splits cleanly into two questions: is it wrong? and is it slow? Different tools for each.

9.1 "My query returns the wrong data"

Work the pipeline from Idea 2, in order:

  1. Check the row count first. SELECT COUNT(*) at each stage. If adding a join changed the count unexpectedly, you've found the join multiplication bug (4.3) — this catches the most dangerous class of error.
  1. Simplify until it's right, then add back one clause at a time. Start from SELECT * FROM one_table and rebuild. The step where it breaks is the bug.
  1. Suspect NULL. Missing rows that "should be there" is almost always three-valued logic: a <> comparison excluding NULLs, a WHERE on a LEFT JOINed table, or a NOT IN with a NULL in the subquery. Test with IS NULL explicitly.
  1. Check your join grain. Ask "what does one row of this result represent?" If you can't answer in one sentence, the query is confused and your aggregates are probably wrong.
  1. Check operator precedence in mixed AND/OR conditions.
  1. Check for silent type coercion — comparing a text column to a number, or a DATE to a TIMESTAMP (where '2026-01-01' as a timestamp means midnight, so <= '2026-01-01' excludes almost the entire day).

9.2 "My query is slow" — EXPLAIN [DEEP]

sql
EXPLAIN ANALYZE
SELECT c.name, SUM(o.total)
FROM customers c JOIN orders o ON o.customer_id = c.id
WHERE c.country = 'IN'
GROUP BY c.name;

EXPLAIN shows the plan the optimizer chose. EXPLAIN ANALYZE actually runs it and shows real timings and row counts alongside the estimates. Always use ANALYZE (carefully — it executes, so wrap UPDATE/DELETE in a transaction you roll back).

Read a plan inside-out and bottom-up: the innermost/most-indented nodes run first and feed their parents.

What to look for, in priority order:

SignalMeaningUsual fix
Seq Scan on a large tableReading every rowAdd an index on the filtered column — *unless* the query genuinely needs most of the table, in which case a scan is correct and optimal
Estimated rows wildly different from actualThe optimizer is working from bad information, so its plan choice is probably wrongRun ANALYZE tablename to refresh statistics; consider extended statistics for correlated columns
Nested Loop with a large outer row countO(n×m) behaviourUsually a missing index on the join key; hash join is often the right plan at scale
Sort with high cost or disk spillSorting more data than fits in memoryIndex that provides the order, or increase work memory, or reduce the row count first
The most time in one nodeYour actual bottleneckEverything else is noise — optimize only this

The crucial discipline: measure, then change one thing, then measure again. Query optimization by intuition is unreliable even for experts, because the optimizer's decisions depend on data distribution you can't see by reading SQL.

9.3 Indexes: the main performance lever [DEEP]

An index is a separate, ordered data structure (usually a B-tree) mapping column values to row locations — conceptually the index at the back of a book. It turns "read all 10 million rows" into "walk down a few levels of a tree."

sql
CREATE INDEX idx_orders_customer_placed ON orders(customer_id, placed_at DESC);

What to know:

  • Index the columns you filter, join, and sort on — especially foreign keys, which are frequently unindexed by default and are the most common cause of slow joins.
  • Composite index column order matters enormously. An index on (a, b) can serve queries filtering on a, or on a and b — but generally *not* on b alone. Think of a phone book sorted by (last name, first name): useless for finding everyone named "Priya."
  • Indexes cost writes. Every INSERT/UPDATE/DELETE must update every affected index. Unused indexes are pure overhead; audit them.
  • Selectivity matters. An index on a boolean column with a 50/50 split rarely helps — the engine would read half the table anyway.
  • Function-wrapped columns defeat indexes (3.2). WHERE LOWER(email) = ... needs an expression index on LOWER(email).
  • Covering indexes include every column the query needs, so the engine never touches the table at all — a large win for hot queries. [ADVANCED]

10
Internals: How the Engine Executes Your Query
TAG ADVANCED★ INTERVIEW GOLD

Return here after Part 8. This section upgrades Part 2's model to mechanism. None of it is needed to *use* SQL; all of it is what distinguishes someone who writes SQL from someone who understands databases.

10.1 The lifecycle of a query

terminal
SQL text
  → Parser        (syntax → tree; catches typos)
  → Analyzer      (resolve names against the catalog; type-check)
  → Rewriter      (expand views, flatten subqueries, push predicates down)
  → Planner/Optimizer (enumerate plans, cost them using statistics, pick one)
  → Executor      (run the plan tree, pulling rows node by node)
  → Result

The optimizer is the interesting part. It is a cost-based search: for each candidate plan it estimates CPU and I/O cost using stored statistics (row counts, distinct-value counts, histograms of value distribution, correlation). Join ordering alone is combinatorially explosive, so beyond a handful of tables it uses heuristics and genetic/greedy approaches rather than exhaustive search.

Why this matters practically: the plan is only as good as the statistics. Stale statistics after a bulk load is one of the most common causes of a query that was fast yesterday and slow today, and the fix is ANALYZE, not a rewrite.

10.2 How data is actually stored

Rows live in fixed-size pages (commonly 8KB) on disk. The engine reads and caches whole pages in a buffer pool in memory. Consequences:

  • Reading one row costs at least one page read — so row size matters; wider rows mean fewer per page and more I/O for the same row count.
  • Sequential page reads are far cheaper per row than random ones, which is why a sequential scan can beat index lookups when you need a large fraction of the table. That's the optimizer's actual reasoning when it "ignores your index."
  • The buffer pool is why the second run of a query is usually much faster — the pages are already in memory. Always benchmark warm, not cold, or you'll optimize the wrong thing.
  • Row-oriented storage (Postgres, MySQL — optimized for reading whole rows: OLTP) versus column-oriented storage (BigQuery, Snowflake, DuckDB, ClickHouse — optimized for reading a few columns across many rows: analytics). Column stores compress far better and scan far faster for aggregates, which is why analytical warehouses are all columnar. Knowing this distinction is a strong signal.

10.3 How indexes work mechanically

A B-tree (technically B+tree) is a balanced tree of pages. The leaves hold ordered key values with pointers to rows; internal nodes route the search. Depth is logarithmic, so finding one key among a billion rows takes only a handful of page reads.

This explains behaviours that otherwise look arbitrary:

  • Range queries work (BETWEEN, >, <, ORDER BY) because leaves are ordered and linked — you find the start and walk.
  • Leading wildcards fail (LIKE '%x') because you can't locate a starting point in an ordering by prefix.
  • Composite index order matters because the ordering is lexicographic — sorted by the first column, then the second within ties.
  • Indexes can satisfy ORDER BY for free, skipping the sort entirely.

Other index types worth knowing exist [REFERENCE]: hash (equality only), GIN/inverted (full-text search, JSON keys, array containment), GiST/R-tree (geometric and geographic data), BRIN (huge naturally-ordered tables like time series, tiny index size), bitmap (low-cardinality columns in analytics).

10.4 Join algorithms [DEEP for interviews]

The optimizer picks among three, and knowing them explains most plan choices:

AlgorithmHow it worksBest when
Nested LoopFor each row of the outer table, look up matches in the innerOuter side is tiny, inner side has an index on the join key
Hash JoinBuild a hash table from the smaller table in memory, then probe it with the largerLarge unsorted inputs, equality joins. The workhorse of analytics
Merge JoinSort both inputs (or use index order), then walk them in lockstepBoth inputs already sorted on the join key; very memory-efficient

So when you see "Nested Loop" on two million-row tables in a plan, you know immediately why it's slow and what's likely missing.

10.5 The interview-grade narration

*"The parser turns SQL into a tree, the analyzer resolves it against the catalog, the rewriter normalizes it and pushes filters down, and then the cost-based optimizer enumerates plans — join orders, join algorithms, access methods — and estimates each using table statistics before picking one. The executor then pulls rows through that plan tree. Data lives in fixed-size pages cached in a buffer pool, and indexes are B-trees whose ordered leaves make ranges and sorted output cheap. Almost all query tuning is either giving the optimizer a better access path with an index, or giving it better statistics so it estimates correctly."*

11
Transactions, Concurrency, and Production Concerns

11.1 Transactions and ACID [DEEP]

A transaction groups statements so they succeed or fail together:

sql
BEGIN;
  UPDATE accounts SET balance = balance - 500 WHERE id = 1;
  UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;    -- or ROLLBACK to undo everything

ACID is the set of guarantees:

PropertyMeansWhy you care
AtomicityAll statements apply, or none doA crash mid-transfer can't destroy money
ConsistencyConstraints hold before and afterThe database never contains data that violates its own rules
IsolationConcurrent transactions don't see each other's partial workTwo simultaneous operations can't interleave into nonsense
DurabilityOnce committed, it survives a crashAchieved via write-ahead logging (WAL) — the log is flushed before the data pages

The habit that matters: wrap every multi-statement change and every destructive statement in an explicit transaction. It's the only undo you get.

11.2 Isolation levels [DEEP — the most under-known important topic in SQL]

Perfect isolation is expensive, so the standard defines levels trading correctness for concurrency. The anomalies they prevent:

  • Dirty read — seeing another transaction's uncommitted changes.
  • Non-repeatable read — reading the same row twice in one transaction and getting different values.
  • Phantom read — re-running the same query and finding new rows that match.
  • Lost update — two transactions read, modify, and write the same row; one overwrites the other silently.
LevelPreventsNotes
READ UNCOMMITTEDNothingEffectively unused; Postgres treats it as READ COMMITTED
READ COMMITTEDDirty readsPostgres and Oracle default. Each statement sees a fresh snapshot, so two queries in one transaction can disagree
REPEATABLE READ+ non-repeatable readsMySQL/InnoDB default. Whole transaction sees one snapshot
SERIALIZABLEEverythingBehaves as if transactions ran one at a time. Costs throughput and can abort transactions with serialization errors your app must retry

The practical consequence, and it's a real bug in a great deal of production code: read-modify-write in application code is unsafe at default isolation levels. SELECT balance → compute in your app → UPDATE balance can lose the other transaction's update entirely. Fixes: do the arithmetic in SQL (SET balance = balance - 500), lock the row (SELECT ... FOR UPDATE), use a constraint to make the bad state impossible, or use SERIALIZABLE and retry on failure.

Knowing the default isolation level of the database you use, and what it does *not* protect you from, is a genuine senior-level distinction.

11.3 Locks and deadlocks [RECOGNIZE]

Writes take row locks; readers in MVCC databases (Postgres, Oracle, MySQL/InnoDB) don't block writers or vice versa, because readers see a snapshot. A deadlock occurs when two transactions each hold what the other needs; the database detects the cycle and kills one with an error. Prevention: acquire locks in a consistent order everywhere, keep transactions short, and never hold a transaction open across user interaction or a network call to another service.

11.4 Production practices that matter [DEEP as a set]

  1. Always parameterize queries. String-concatenating user input is SQL injection — still the top-ranked class of web vulnerability decades after it was understood. WHERE id = ? with a bound parameter is safe; "WHERE id = " + input is not. This is non-negotiable, and no amount of input escaping is as reliable as parameterization.
  1. Grant least privilege. The application's database user should not be able to DROP TABLE. Separate read-only accounts for reporting.
  1. Migrations, not manual changes. Schema changes live in version-controlled, reviewed, sequentially-applied files. Manual production changes are unreproducible and undocumented by definition.
  1. Backups you have actually restored. An untested backup is a hypothesis. Practise the restore.
  1. Keyset pagination for large offsets. OFFSET 100000 makes the engine generate and discard 100,000 rows. Instead: WHERE (created_at, id) < (:last_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20.
  1. Watch N+1 query patterns. An ORM that runs one query per row of a loop is Idea 1's loop-thinking made expensive. Fix with a join or a batched IN (...).
  1. Monitor slow queries. Enable slow-query logging or pg_stat_statements — you cannot optimize what you don't measure, and the slowest query is rarely the one you'd guess.
  1. Time zones: store UTC, convert at the edges. And use a real timestamp type, never text.

When SQL Is and Isn't the Right Tool
TAG DEEP

Being able to argue *against* your tool is a mark of genuine understanding.

SQL and a relational database are right when: the data has structure and relationships (nearly all business data does); you need ad-hoc queries you didn't anticipate at design time; correctness under concurrency matters (anything involving money, inventory, bookings); you want the database to enforce integrity; the dataset fits on one machine or a modest cluster — which today means it can be very large indeed.

A different tool may be better when:

SituationWhy SQL strugglesAlternative
Deeply hierarchical or graph-shaped traversal (social graphs, recommendations, "friends of friends of friends")Recursive joins get expensive and awkwardGraph databases (Neo4j)
Simple key-value lookups at extreme throughput; caching; ephemeral session dataThe overhead of a full relational engine buys you nothingRedis, DynamoDB
Genuinely schemaless, highly variable documents where structure differs per recordYou'd be fighting the schemaDocument stores (MongoDB) — but note that Postgres JSONB covers a large fraction of this need without giving up joins and transactions
Full-text relevance search, fuzzy matching, facetingSQL's text search is basic by comparisonElasticsearch, OpenSearch
Massive append-only time-series or event streamsRow-store overhead per event; different access patternTimescaleDB, ClickHouse, InfluxDB
Petabyte-scale analytical scansRow storage reads columns you don't needColumnar warehouses (BigQuery, Snowflake, DuckDB)
Writes exceeding what one primary can absorb, needing horizontal scale-outTraditional single-primary architectureDistributed SQL (CockroachDB, Spanner, Vitess) — often better than abandoning SQL

The honest historical lesson: many organizations adopted NoSQL in the 2010s for scale they never reached, and paid for it in lost joins, lost transactions, and application code reimplementing consistency badly. The reverse mistake also exists — forcing a genuine graph or search problem into SQL. Choose based on your access patterns and consistency needs, not on which technology sounds modern.

Also worth knowing SQL's real weaknesses rather than defending it reflexively: dialect fragmentation makes portability harder than the standard implies; complex queries are hard to test, version, and modularize compared with application code; there's no good story for reuse (no functions-and-modules discipline, so copy-paste is rampant); error messages are frequently poor; and the language's clause order genuinely does not match its evaluation order, which makes it harder to learn than it needed to be.
