Where JavaScript Came From
TAG DEEP

Every strange thing about JavaScript is a historical artifact. Knowing the history converts "this language is broken" into "this language has scars, and here's which ones to avoid."

The lineage

YearWhat happenedWhy it still affects you
1995Brendan Eich writes it at Netscape in ~10 days, under orders to make it "look like Java" while actually borrowing from Scheme (first-class functions, closures) and Self (prototypes)The two halves of the language: a serious functional/prototypal core wearing a C-family costume. == coercion, typeof null === "object", and hoisting are ten-day-deadline artifacts that could never be removed
1995Named JavaScript purely for marketing — Java was hot. It is unrelated to JavaTwenty years of confused interviews
1996–99Microsoft ships JScript; ECMAScript standardization begins (hence "ES"). ES3 (1999) is the baseline for a decadeThe name ECMAScript exists because "JavaScript" was a Sun trademark
2000–05Browser incompatibility hell. jQuery (2006) exists almost entirely to paper over DOM API differences and provide a usable selector engineWhy every senior dev has jQuery reflexes, and why querySelector + fetch made it unnecessary
2005AJAX named; Gmail/Maps prove the browser can host applicationsThe moment the browser stopped being a document viewer. Everything after is consequence

2009Node.js puts V8 on the server; npm followsJS escapes the browser. One language across the stack — the reason full-stack JS exists

What JavaScript actually invented — and what it inherited

It invented almost none of its good ideas: closures and first-class functions are Scheme's, prototypes are Self's, the syntax is C/Java's. What it *did* uniquely get was ubiquity — the only language that runs natively in every browser on Earth, and therefore the only one with a guaranteed distribution channel of billions of devices. That accident of position, not language quality, is why it won.

The governing constraint: "don't break the web"

This is the single most important thing to understand about JS's evolution, and it's the same principle you met in the HTML curriculum. Millions of pages will never be updated, so nothing can ever be removed. var, ==, with, implicit globals, typeof null — all still there, forever. New features must be added *alongside* the mistakes.

Two direct consequences: (1) the language has multiple ways to do everything, and "modern JS" is mostly a set of *conventions about which subset to use* — const/let not var, === not ==, async/await not callbacks; (2) "use strict" and ES modules exist as opt-in stricter dialects, because they could change behaviour only for code that asked for it.

Interview-grade framing: *"JavaScript's quirks aren't carelessness so much as a permanent backward-compatibility guarantee. It was written in ten days, standardized before it was designed, and can never remove a mistake — so evolution happens by adding better paths and socially deprecating the old ones."*

02
The Core Mental Model
TAG DEEP

Five ideas. Everything downstream is detail.

Idea 1: Variables hold values or references, and the difference explains half your bugs

Primitives (number, string, boolean, null, undefined, symbol, bigint) are copied by value. Objects (including arrays and functions) are copied by reference — the variable holds a pointer, not the thing.

js
let a = { n: 1 };
let b = a;        // b points at the SAME object
b.n = 2;
a.n;              // 2  ← you mutated one object through two names

let x = [1,2,3];
let y = [...x];   // NEW array (shallow copy) — y[0] is independent

Consequences you'll hit constantly:

  • const obj = {} prevents rebinding obj, not mutation of its contents. const is not immutability.
  • Passing an object into a function passes the reference — the function can mutate your data. This is the #1 source of "why did my state change?" bugs.
  • Spread and Object.assign are shallow: nested objects are still shared. structuredClone(obj) gives you a deep copy.
  • React's re-render logic is built on identity comparison, which is why "mutate then setState" silently does nothing while "create a new object" works. That's not a React rule; it's this rule.

Idea 2: Scope is lexical, and closures fall out of it for free

Where a variable is *visible* is determined by where the code is written, not who calls it. Every function, when created, keeps a live link to the scope it was defined in — that combination of function + retained scope is a closure.

js
function counter() {
  let count = 0;                 // lives in counter's scope
  return () => ++count;          // this function keeps that scope alive
}
const next = counter();
next(); next();                  // 1, 2  ← count survives after counter() returned

Closures are not an advanced feature; they're a consequence of lexical scope plus functions being values. Every callback, every event handler, every React hook, every module-private variable is a closure. If you understand this one idea properly, useState's "stale value" bugs stop being mysterious.

Idea 3: Objects delegate to other objects — the prototype chain

There are no classes underneath. Every object has an internal link to another object (its prototype). Property lookup walks that chain until found or until null:

terminal
myArray → Array.prototype → Object.prototype → null

That's why [].map exists without being on your array: it's found one link up. class syntax (ES6) is real and useful but is sugar over this mechanism — it creates a constructor function and wires prototypes. Understanding the chain is what makes instanceof, method inheritance, and "why is my method undefined?" tractable.

Idea 4: this is decided by the call, not by the definition

The most-failed interview topic. this inside a normal function is determined at call time:

Call formthis is
obj.method()obj — the object left of the dot
fn()undefined in strict mode/modules; the global object otherwise
new Fn()The newly created object
fn.call(x) / fn.apply(x) / fn.bind(x)Explicitly x
Arrow functionNot its own — inherited lexically from where it was written

Which gives you the classic bug and its fix in one:

js
const user = {
  name: 'Utkarsh',
  greetBroken() { setTimeout(function () { console.log(this.name); }, 0); }, // undefined
  greetFixed()  { setTimeout(() => console.log(this.name), 0); }             // works
};

The arrow function fixes it not by magic but by *not having* this — it reads the enclosing one. That's the whole reason arrows were added.

Idea 5: One thread, one call stack, and a queue — the event loop

JavaScript executes on a single thread. There is one call stack; only one thing runs at a time. So how does it do network requests, timers, and clicks without freezing?

It doesn't do them itself. The runtime (browser or Node) does — with real threads underneath — and hands results back as callbacks. The event loop's job: when the call stack is empty, take the next queued callback and run it.

terminal
        ┌──────────────┐
run ───▶│  call stack  │  (one thing at a time)
        └──────────────┘
               ▲
               │ event loop: when stack is empty, take next
        ┌──────┴─────────────────────────────┐
        │ microtasks (promises) — drained FIRST, fully │
        │ macrotasks (setTimeout, I/O, events) — one per tick │
        └────────────────────────────────────┘

Two consequences that answer most async confusion:

  • Nothing is interrupted. A long synchronous loop blocks timers, clicks, and rendering — because they're all waiting for the stack to empty. "JS is non-blocking" refers to I/O, not to your code.
  • Microtasks jump the queue. All pending promise callbacks run before the next setTimeout, which is exactly why this prints 1, 4, 3, 2:
js
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
console.log(4);

03
Values, Types, and Coercion

3.1 The type system [DEEP concept, REFERENCE the trivia]

Dynamically typed: values have types, variables don't. Seven primitives (number, string, boolean, null, undefined, symbol, bigint) plus objects. typeof null === "object" is a 1995 bug preserved forever (Part 1).

One number type: IEEE-754 doubles. Hence 0.1 + 0.2 === 0.30000000000000004, and hence: never store money in a float. Use integer paise/cents, or a decimal library. Given your fintech and invoicing work (Razorpay amounts are integers in paise for exactly this reason), this one is load-bearing, not academic.

3.2 Coercion, and the rule that makes it a non-issue [DEEP]

JS converts types implicitly, and the rules are genuinely arbitrary ([] + {}, "5" - 2, null >= 0). The professional response is not to memorize the table — it's to not rely on it:

  • Always ===, never ==. The one defensible exception is x == null to catch both null and undefined.
  • Convert explicitly: Number(x), String(x), Boolean(x).
  • Know the eight falsy values by heart, because they cause real bugs: false, 0, -0, 0n, "", null, undefined, NaN. Everything else — including [], {}, and "0" — is truthy.
  • The falsy trap that will bite you: if (count) is false when count === 0, which is usually a valid value. Use if (count !== undefined) or ??.

?? (nullish coalescing) vs ||: || falls through on any falsy value, ?? only on null/undefined. const limit = input ?? 10 is correct where input || 10 would wrongly override a deliberate 0.

3.3 Declarations [DEEP]

varletconst
ScopeFunctionBlockBlock
HoistingHoisted, initialized undefinedHoisted but in TDZ — throws if accessed before declarationSame as let
RebindableYesYesNo

Rule: const by default, let when you must reassign, var never. The TDZ (temporal dead zone) is a deliberate improvement: var's silent undefined hid bugs; let throws a clear error instead.

3.4 Modern syntax you'll read constantly [RECOGNIZE]

js
const { name, email: mail, role = 'user' } = user;      // destructure + rename + default
const [first, ...rest] = items;
const merged = { ...defaults, ...overrides };            // later wins
const label = `${count} case${count === 1 ? '' : 's'}`;  // template literal
const city = user?.address?.city ?? 'Unknown';           // optional chaining + nullish

Optional chaining is worth a note: it short-circuits to undefined instead of throwing "cannot read property of undefined" — the single most common runtime error in JS. It replaced whole paragraphs of defensive && chains.

04
Functions, Scope, Closures

4.1 Functions are values [DEEP]

They can be assigned, passed, returned, and stored in objects and arrays. This is the foundation of callbacks, higher-order functions, event handlers, middleware, and every hook you use. It comes from Scheme (Part 1) and is the language's best feature.

js
const twice = fn => x => fn(fn(x));       // takes a function, returns a function
const inc = n => n + 1;
twice(inc)(5);                            // 7

4.2 Arrow vs normal functions [DEEP]

functionArrow
thisDynamic, set by call siteLexical — inherited, cannot be rebound
argumentsAvailableNot available
HoistedDeclarations are fully hoistedNo (it's a const assignment)
Usable as constructor / method with thisYesNo

Practical rule: arrows for callbacks and anything nested inside a method; normal functions for object methods and anything needing dynamic this. The reason arrows exist at all is Idea 4 — they were added specifically to kill var self = this.

4.3 Closures in practice [DEEP]

Four patterns you already use without naming them:

js
// 1. Private state (the module pattern)
const makeStore = () => { let state = {}; return {
  get: k => state[k], set: (k,v) => { state = {...state, [k]:v}; } }; };

// 2. Function factories / partial application
const withPrefix = p => msg => console.log(`[${p}] ${msg}`);
const logDb = withPrefix('db');

// 3. Memoization — the cache lives in the closure
const memo = fn => { const c = new Map();
  return x => c.has(x) ? c.get(x) : (c.set(x, fn(x)), c.get(x)); };

// 4. Debounce — the timer id lives in the closure
const debounce = (fn, ms) => { let t; return (...a) => {
  clearTimeout(t); t = setTimeout(() => fn(...a), ms); }; };

That debounce is worth writing from memory once; it's the most-asked closure question in interviews and it's genuinely useful in every search box you build.

The classic closure bug (and the reason let was introduced): var is function-scoped, so all three callbacks close over the *same* i. let creates a new binding per iteration, so each closure captures its own.

4.4 Parameters [RECOGNIZE]

js
function search(q, { limit = 20, sort = 'date' } = {}) { }   // destructured options w/ defaults
const sum = (...nums) => nums.reduce((a,b) => a+b, 0);        // rest

Common mistake: a mutable default that's shared — less severe in JS than Python, but function f(arr = []) creates a fresh array per call, so JS gets this right where Python doesn't. Worth knowing since you're learning both.

4.5 Purity and side effects [DEEP as discipline]

A pure function's output depends only on its inputs and it mutates nothing outside itself. Pure functions are trivially testable, cacheable, and safe to move. The practical discipline: push side effects (network, DOM, storage, logging) to the edges of your code and keep the middle pure. This is the single habit that most improves testability, and it's the principle behind React's render model, reducers, and functional pipelines.

05
Objects, Prototypes, Classes

5.1 Objects [RECOGNIZE]

js
const key = 'status';
const case_ = { id: 7, [key]: 'open', hear() { return this.id; } };
Object.keys(o); Object.values(o); Object.entries(o);   // iterate
const { id, ...rest } = case_;                          // omit a key
Object.freeze(o);                                       // shallow immutability

Note Object.entries(o).map(...) — converting objects to arrays to use array methods, then back with Object.fromEntries. That round-trip is the standard idiom for transforming object shapes.

5.2 The prototype chain, concretely [DEEP]

js
const animal = { speak() { return `${this.name} makes a sound`; } };
const dog = Object.create(animal);      // dog's prototype IS animal
dog.name = 'Rex';
dog.speak();                            // found one link up the chain
Object.getPrototypeOf(dog) === animal;  // true

Lookup walks up; assignment does not — dog.speak = ... creates an own property that shadows the prototype's. That asymmetry explains most confusion about inheritance in JS.

5.3 Classes [RECOGNIZE syntax, DEEP that it's sugar]

js
class Case {
  #notes = [];                                  // truly private field
  static from(row) { return new Case(row.id); } // static factory
  constructor(id) { this.id = id; }
  get summary() { return `Case ${this.id}`; }   // getter — accessed as .summary
  addNote(n) { this.#notes.push(n); return this; }
}
class Appeal extends Case {
  constructor(id, court) { super(id); this.court = court; }
}

Methods live on Case.prototype, shared by all instances — not copied per object. extends links prototypes. super calls up the chain. So classes are a readability win over Object.create plumbing, nothing more, and knowing that is the interview answer.

Prefer composition over inheritance. Deep class hierarchies are brittle; passing collaborating objects/functions in is more flexible. Most modern JS codebases (and all of React) chose composition — worth being able to argue why.

06
Arrays and Data Transformation

6.1 The model [DEEP]

Stop writing for loops for transformations. Think in three verbs — this is the same mental shift you already made with SQL, and it's the closest analogy available to you:

VerbSQL analogueReturns
mapSELECT exprNew array, same length
filterWHERENew array, subset
reduceGROUP BY / aggregateAny single value
js
const hearings = cases
  .filter(c => c.status === 'open')                  // WHERE
  .map(c => ({ id: c.id, next: c.hearings[0] }))     // SELECT
  .sort((a,b) => a.next.localeCompare(b.next));      // ORDER BY

const byCourt = cases.reduce((acc, c) => {           // GROUP BY
  (acc[c.court] ??= []).push(c); return acc;
}, {});

reduce is the general case — map and filter are both special cases of it. Understand (accumulator, current) => newAccumulator and it stops being scary.

6.2 Mutating vs non-mutating [DEEP — bug source]

Mutates in placeReturns new
push, pop, shift, unshift, splice, sort, reversemap, filter, slice, concat, flat, spread, toSorted, toReversed

sort and reverse mutating is a trap — list.sort() reorders the original, which in React means state you thought was untouched has changed. Use [...list].sort() or the newer toSorted().

6.3 Other collections [RECOGNIZE]

Map — keys of any type, preserves insertion order, .size, no prototype-key collisions. Prefer over plain objects for real key-value stores. Set — unique values; [...new Set(arr)] is the standard dedupe. Object.groupBy for grouping without the reduce boilerplate.

6.4 Common mistakes

  • forEach when you wanted map (returns undefined).
  • async inside forEach — it does not wait. Use for...of with await, or Promise.all(arr.map(async ...)).
  • Mutating during iteration.
  • Reaching for a library for things now native (flat, groupBy, structuredClone).

07
Asynchrony: The Event Loop in Practice

7.1 Why async exists at all [DEEP]

One thread (Idea 5) + operations that take time (network, disk, timers) = if you waited synchronously, the UI would freeze on every request. So the runtime does the waiting off-thread and calls you back. Async in JS isn't about parallelism — it's about not blocking the one thread you have.

7.2 The three generations [DEEP on why each replaced the last]

js
// 1. Callbacks (1995–) — worked, but nesting and error handling didn't compose
getUser(id, (err, user) => { if (err) return cb(err);
  getCases(user.id, (err, cases) => { /* callback hell */ }); });

// 2. Promises (ES6) — a first-class VALUE representing a future result, so it can be
//    returned, stored, combined, and chained; errors propagate down one .catch
getUser(id).then(u => getCases(u.id)).then(render).catch(showError);

// 3. async/await (ES2017) — the same promises, written in linear form
async function load(id) {
  try {
    const user  = await getUser(id);
    const cases = await getCases(user.id);
    return render(cases);
  } catch (e) { showError(e); }
}

The key insight most people miss: async/await is not a third mechanism. An async function always returns a promise; await just pauses that function and resumes it in a microtask when the promise settles. Everything about promises still applies — which is why understanding promises properly is non-optional.

7.3 Concurrency patterns [DEEP — the sequential-await mistake]

js
// SLOW — 3 sequential round trips
const a = await getA(); const b = await getB(); const c = await getC();

// FAST — all three start immediately, then wait for all
const [a, b, c] = await Promise.all([getA(), getB(), getC()]);

Awaiting in a loop when the operations are independent is the most common real-world async performance bug. Promise.all rejects if *any* rejects; Promise.allSettled gives you every outcome (right for "fetch 50 things, tolerate failures" — e.g. your eCourts sync); Promise.race/any for timeouts and fallbacks.

7.4 Errors, timeouts, cancellation [RECOGNIZE, one [DEEP] gotcha]

js
const ctrl = new AbortController();
setTimeout(() => ctrl.abort(), 5000);
const res = await fetch(url, { signal: ctrl.signal });
if (!res.ok) throw new Error(`HTTP ${res.status}`);   // ← fetch does NOT throw on 404/500
const data = await res.json();

The [DEEP] gotcha in that snippet: fetch only rejects on network failure, not on HTTP error status. A 500 resolves normally with res.ok === false. Every JS developer has shipped this bug once. And an unawaited async call that rejects becomes an unhandled rejection — silent in browsers, fatal in modern Node.

7.5 Exercise

Write a fetchWithRetry(url, { retries = 3, timeout = 5000 }) that: times out via AbortController, retries with exponential backoff, doesn't retry 4xx (client errors won't fix themselves), throws a useful error on final failure. This single function exercises promises, closures, error handling, and cancellation — and you'll reuse it in every project you build.

08
The Browser: DOM, Events, and Why Frameworks Exist

8.1 The DOM is an API, not the language [DEEP]

JS the language has no concept of a document. document, window, fetch, localStorage are all host-provided APIs — which is why the same language runs in Node with none of them. Keeping that separation clear is what makes "does this code run on the server?" answerable.

js
const el = document.querySelector('.card');          // CSS selectors, no jQuery needed
el.textContent = 'safe';                             // ← always prefer over innerHTML
el.classList.toggle('is-open');
el.dataset.caseId = 7;                               // data-case-id
const node = tpl.content.cloneNode(true);            // <template> for repeated markup

textContent vs innerHTML is a security boundary, not a style choice. innerHTML with any user-supplied string is an XSS vulnerability. Given you're building a real app with user data, treat innerHTML as a decision requiring justification and sanitization.

8.2 Events [DEEP]

An event captures down the tree from window to the target, fires on the target, then bubbles back up. Consequences:

js
list.addEventListener('click', e => {                 // ONE listener for N children
  const btn = e.target.closest('[data-id]');          // event DELEGATION
  if (!btn) return;
  open(btn.dataset.id);
});

Delegation is the pattern to internalize: it works for elements added later, and it replaces N listeners with one. e.preventDefault() stops the browser's default action (form submit, link navigation); e.stopPropagation() stops the bubbling — different things, frequently confused, and a common interview question.

8.3 Why frameworks exist [DEEP — this is the bridge to your actual work]

Vanilla DOM manipulation has one structural problem: you must manually keep the DOM in sync with your data, from every code path that changes it. With three pieces of state and five views, the number of update paths explodes, and bugs are always "this one place forgot to update."

React's proposition is a single idea: UI is a function of state. You describe what the DOM should look like for the current state; the framework computes the difference and applies it. Every React concept you already use follows from that:

React thingThe vanilla problem it solves
ComponentsAd-hoc functions creating and wiring DOM by hand
State + re-renderManual, easily-forgotten DOM updates
Keys in listsIdentity tracking when reordering children
useEffectLifecycle-tied side effects and their cleanup (removing listeners, aborting fetches)
Reference equality in deps/memoIdea 1 — new object identity per render

So do Part 9's vanilla app before reaching for a framework again. It's the only way to feel the problem React solves, which is the difference between using React and understanding it.

10
Debugging Playbook
TAG DEEP

The decision tree

Cannot read properties of undefined (reading 'x') — the most common JS error. Something in the chain before .x is undefined. Read the stack trace's top frame, log the object *one level up*, and fix the cause (usually a wrong API shape assumption or an async value read before it arrived). ?. silences the symptom; only use it where absence is genuinely valid.

undefined is not a function — typo, wrong import shape (default vs named), or this lost (Idea 4).

"My value is stale / didn't update." Almost always Idea 1 (mutated instead of replaced, so identity didn't change) or Idea 2 (a closure captured an old value). In React specifically: mutation of state, or a stale closure in a callback with missing deps.

"My async code runs in the wrong order." Reason it out with Idea 5: sync code first, then all microtasks (promises/awaits), then one macrotask (timers). Add console.log markers before/after every await and read the actual order rather than the intended one.

"It works locally, fails in production." Env vars missing, CORS, HTTPS-only APIs, minification exposing a timing bug, or a browser-only API running during SSR (window is not defined — a Next.js classic).

Silent failure, nothing in console. An unhandled promise rejection (add window.addEventListener('unhandledrejection', ...)), an error swallowed by an empty catch, or an event listener attached before the element existed.

The tools worth mastery

console.table for arrays of objects; console.group; debugger; statements and DevTools breakpoints (conditional breakpoints are the underrated one); the Network tab for the actual request/response rather than what you think you sent; and Sources → watch for stepping through closures to see captured values. Learning to step through code beats adding logs, and it's the habit that most separates fast debuggers from slow ones.

Internals
TAG ADVANCED★ INTERVIEW GOLD

11.1 How V8 runs your code

Parse → AST → Ignition compiles to bytecode and starts executing immediately → hot functions get optimized by TurboFan into machine code, using observed types → if an assumption breaks (a function that always got numbers suddenly gets a string), V8 deoptimizes back to bytecode.

The actionable consequence: V8 optimizes *predictable* code. Objects with consistent shapes (same properties, same order — "hidden classes") and functions called with consistent types run dramatically faster than polymorphic ones. You don't micro-optimize for this, but it explains why "just make it dynamic" has a real cost, and why TypeScript's discipline often incidentally produces faster code.

11.2 Memory and leaks

Automatic GC (generational, mark-and-sweep): unreachable objects are collected. So leaks in JS are always unintended reachability:

  • Listeners never removed (the closure keeps the whole scope alive — including DOM nodes).
  • Timers/intervals never cleared.
  • Growing caches/arrays with no eviction.
  • Detached DOM nodes still referenced by a variable.

WeakMap/WeakSet hold keys weakly, so they don't prevent collection — the right tool for metadata attached to objects you don't own. Diagnose with DevTools Memory → heap snapshot comparison.

11.3 The event loop, precisely [DEEP for interviews]

One turn: (1) run the current macrotask to completion; (2) drain the entire microtask queue — including microtasks queued by microtasks, which is why an infinite microtask loop hangs the page permanently; (3) in browsers, run requestAnimationFrame callbacks and then render if needed; (4) take the next macrotask.

Therefore: setTimeout(fn, 0) means "after the current task and all microtasks," not "immediately" — and the minimum clamps to ~4ms after nesting. Node adds process.nextTick (before other microtasks) and distinct phases (timers, pending callbacks, poll, check/setImmediate, close) — [ADVANCED], but knowing the phases exist is a real Node signal.

11.4 Modules [DEEP]

ESM (import/export) is statically analyzable — resolved before execution, which enables tree-shaking and circular-import handling, and its imports are *live bindings*. CommonJS (require/module.exports) is dynamic and synchronous, evaluated at call time, returning a copy of the value. That difference is why the Node ecosystem's ESM/CJS transition has been so painful, and why "type": "module", .mjs, and dual builds exist.

Bundlers exist because HTTP/1.1 made hundreds of module requests slow and because browsers had no module system until 2017 — plus transpilation for older targets. With ESM and HTTP/2, "why do I need a bundler at all?" is now a legitimate question for small projects, which is exactly what Vite's dev server bets on.

Production

12.1 TypeScript [DEEP as a decision]

TS adds a compile-time type layer and erases entirely at runtime — no runtime safety. What you get: errors at build time instead of in production, real autocomplete, and types as executable documentation. What you pay: a build step, config, and the type-gymnastics tax on complex generics.

The critical implication people miss: because types vanish at runtime, external data is unverified. A typed fetch response is a *claim*, not a check. Validate boundaries at runtime (Zod or equivalent) — API responses, form input, env vars, webhook payloads. Type-safe-in-editor plus unvalidated-at-runtime is a false sense of security, and it's exactly the gap that bites in real apps like yours with Supabase and Razorpay payloads.

12.2 Testing [RECOGNIZE]

Unit tests for pure logic (cheap, fast, plentiful); integration tests for modules working together; a small number of end-to-end tests (Playwright) for critical user paths. Test behaviour, not implementation — a test that breaks on every refactor is a liability. Vitest/Jest for the first two.

13
When Not to Use JavaScript
TAG DEEP

Right tool when: anything in a browser (no alternative that isn't compiled to JS/WASM); full-stack teams wanting one language; I/O-heavy services (the event loop is genuinely excellent at many concurrent connections); real-time (WebSockets); tooling and scripting where npm's ecosystem wins.

Wrong or questionable when:

  • CPU-bound work — single thread, and heavy computation blocks everything. Worker threads and WASM help; Python/Go/Rust are often just better. Your ETL and data-crunching work belongs in Python, not Node.
  • Data science / ML — the ecosystem simply isn't there. numpy/pandas/PyTorch have no real JS equivalent.
  • Precise decimal arithmetic — floats. Money needs integers or a decimal library (Part 3.1).
  • Long-lived systems needing strong guarantees — dynamic typing plus a fast-churning ecosystem; TS mitigates, doesn't eliminate.
  • Small static sites — often no JS needed at all; HTML/CSS does it, and shipping zero JS is faster than any framework.
  • Where the dependency tree is the risk — a 2MB node_modules for a 50-line script is a real supply-chain and maintenance cost.

Honest additional weaknesses worth being able to name: ecosystem churn, node_modules weight, ESM/CJS fragmentation, and the fact that "JavaScript fatigue" is a real cost of the platform's speed of change.

If you can deliver these aloud — WHAT → WHY IT EXISTS → ONE CONCRETE CONSEQUENCE — you are interview-ready. Answer before flipping; nailed cards dim.
